# Zero-downtime upgrades

## Goal

A hosted Chopin should ship new versions to real people without interrupting them. A deploy should sign nobody out. An open tab should show no error and lose no edit, Decision answer or Planner turn that was already under way. Planners and builds on connected machines should carry on. Eventually several Chopin processes should share one database, so that a deploy moves documents between processes instead of restarting the only one.

This is a design document and changes no code. It records what a restart does today, the published practice the design draws on, the alternatives, and a design in four stages that can each ship on its own:

1. **Strictly invisible restarts on one server.** A second process starts and warms beside the first. The first keeps serving while its running turns finish and its state is committed, then, once the proxy has stopped routing to it, releases the writer lease, and the second takes over within the 1.5 s reconnect grace. Remote Planner sessions, every acknowledged Planner request that has not started (Chat messages, comment notes, task drafts and `invoke_planner` calls), MCP sessions and open tabs survive.
2. **Release safety.** A readiness endpoint, a smoke test of the built image in CI, schema and document-format compatibility with the previous release, automatic rollback, and feature flags.
3. **Several processes.** Each root document has one owner process, fenced by a lease in PostgreSQL, and its traffic reaches that owner. A deploy moves documents one at a time.
4. **Connected machines.** The connector and its agents update only when idle and resume afterwards, and the server keeps a stated support window for older connectors and agent clients.

Maintainer decisions, recorded in [Open questions](#open-questions) 1 to 4 and applied throughout: a deploy must be strictly invisible, so processes must overlap; remote Planner sessions are persisted, and a login is still restored from its browser cookie only, which leaves two bounded remote-Planner exceptions (open question 3 (h)); the known hosted deployment runs Docker Compose with Caddy 2 on one VM, and the [reference deployment](#reference-deployment) shows the overlap it needs.

Every `path:line` citation was read in this checkout. **(inferred)** marks a conclusion drawn from code that was not run. The two runtime observations made for this document (the close code Bun sends on shutdown, and the reference fetches) are marked where they appear. Unknowns are collected in [Open questions](#open-questions).

## Today

### How a deploy runs

- [Self-hosting](self-hosting.md) states the boundary at `docs/self-hosting.md:17-18`: "One active Chopin process may write to a database. Horizontal application scaling and zero-downtime rolling deployment are not supported." Migrations are forward-only with no automated schema rollback (`docs/self-hosting.md:21`).
- The documented upgrade is: back up the database and keep the current image, stop the old process, start the new image, whose entrypoint migrates before serving (`docs/self-hosting.md:716-727`). Returning to an older image "may require restoring the pre-upgrade database".
- The image runs `bun apps/server/src/storage/migrate.ts && exec bun apps/server/src/main.ts` (`Dockerfile:73`). The migration script loads the full configuration but does not take the writer lease (`apps/server/src/storage/migrate.ts:1-16`).
- `compose.yaml` exposes port 8787 without publishing it, restarts `unless-stopped`, and allows `stop_grace_period: 15s` between SIGTERM and SIGKILL (`compose.yaml:29-35`). It declares no proxy. "Coolify supplies the public proxy" (`docs/self-hosting.md:611`), and that deployment automation "do[es] not live in this repository" (`docs/preview-testing.md:3-6`).
- **There is no Caddyfile in this checkout and no text about 502s during startup.** Caddy appears only as an example proxy (`docs/self-hosting.md:290`, `docs/self-hosting.md:310`) and in two connector test comments that say a proxy "answers for a Chopin that went away with 502" (`apps/connector/src/run.test.ts:811`, `apps/connector/src/status.test.ts:432`). The maintainers have since described the known hosted deployment: Docker Compose with Caddy 2 as the reverse proxy on a single VM, deployed by a script that runs `docker compose pull` and then `up --detach`, with `stop_grace_period: 30s` and a container health check. Its operators control the proxy configuration, which is not in this repository. The design below is therefore platform-neutral, and [Reference deployment](#reference-deployment) shows the Compose and Caddy setup that achieves the overlap. What the proxy answers while no upstream exists is still unverified (open question 1).
- CI builds the image with `push: false` and never starts it (`.github/workflows/ci.yml:476-494`). The only release workflow publishes the `chopin` CLI on `cli-v*` tags (`.github/workflows/release-cli.yml:8-10`). There is no server deploy, staging or rollback automation in the repository.

### The window in which nothing listens

On SIGTERM the old process stops its listener almost first (`apps/server/src/main.ts:1887`). The replacement opens its listener only after the following steps:

1. migrations (`Dockerfile:73`);
2. `storage.health()`, which re-verifies every migration checksum (`apps/server/src/main.ts:2897`, `apps/server/src/storage/postgres/adapter.ts:788-793`);
3. acquiring `chopin:writer` (`apps/server/src/main.ts:2905-2911`);
4. the session and owner reset (`apps/server/src/main.ts:2916-2921`);
5. clearing child conversations (`apps/server/src/main.ts:2923`);
6. experiment recovery (`apps/server/src/main.ts:2948`);
7. `listen()` (`apps/server/src/main.ts:2949`).

The downtime is therefore the rest of the old drain, plus container replacement, plus all of the new process's startup. No listener exists at all during that time. Its length was not measured for this document.

The new process cannot start early. If the lease is held it throws "another Chopin instance owns the database" (`apps/server/src/main.ts:2911`), and the catch exits with status 1 (`apps/server/src/main.ts:2934-2940`). `apps/server/src/storage/postgres/startup.test.ts:136-139` asserts that exit, and `:145-149` asserts that a SIGTERM of the holder lets a replacement start. After a crash, the row stays unexpired for up to `LEASE_TTL_MS = 30_000` (`apps/server/src/main.ts:178`), and every start in that time exits 1, because `#acquire` takes only an expired row or its own (`apps/server/src/storage/postgres/adapter.ts:1830-1861`) **(inferred)**.

### Drain order

`drain()` (`apps/server/src/main.ts:1872-1929`) runs from `signal()` (`apps/server/src/main.ts:1931-1939`) and has no deadline of its own.

| Step | Code                                | Effect                                                                                                                                                                           |
| ---- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `apps/server/src/main.ts:1886`      | Planner attachments are told the server is going down, so no link withdraws a question (`apps/server/src/harness/remote/attachments.ts:379-385`)                                 |
| 2    | `apps/server/src/main.ts:1887`      | `server.stop(true)` closes the listener and every socket                                                                                                                         |
| 3    | `apps/server/src/main.ts:1888-1894` | Timers stop, and in-flight research recovery and session cleanup are awaited                                                                                                     |
| 4    | `apps/server/src/main.ts:1895-1906` | Each open room's conversation runtime stops and `Service.close` runs                                                                                                             |
| 5    | `apps/server/src/main.ts:1907-1912` | Summaries and document history flush, and the live-build, readiness and spike workers close                                                                                      |
| 6    | `apps/server/src/main.ts:1913-1920` | Decision answers stay stored for the next process, the job runner shuts down, and owner bindings and attachments are revoked                                                     |
| 7    | `apps/server/src/main.ts:1921-1926` | Harnesses shut down, lease renewal stops, the lease is released by setting its expiry to the epoch (`apps/server/src/storage/postgres/adapter.ts:1920-1930`), and storage closes |

Effects on clients:

- **Close code (observed).** Bun closes every socket with code **1001** and reason "Server closed" on `server.stop(true)`. A throwaway script outside the repository, run with the pinned Bun 1.4.4, showed this as `code=1001 reason="Server closed" wasClean=true` on the client and 1001 in the server's close handler. `server.stop(false)` left the socket open for at least three seconds. Nothing in `drain()` sets a code itself.
  - 1001 is also the agent link's `LINK_CLOSE.unresponsive` (`packages/agent-link/src/protocol.ts:51`).
  - The browser treats every close except 4404 as a loss and retries (`apps/web/src/wire.ts:213-224`).
- **In-flight Planner turns are aborted.** `Service.close` (`apps/server/src/plan/service.ts:2405-2419`) runs `Chat.close`, which fails queued work with "The document closed." and aborts the running turn (`apps/server/src/chat/service.ts:3094-3120`, abort at `:3112`). Under `HARNESS=atomic` and `copilot-sdk`, the harness session lives in this process and cannot be resumed (`docs/self-hosting.md:154-156`, `docs/hosted-agent.md:811-813`). An interrupted turn is never replayed (`AGENTS.md:246-247`).
- **Each room writes a final commit and a full checkpoint** (`apps/server/src/plan/service.ts:2414-2415`). Every fenced write for one lease takes the same advisory lock (`apps/server/src/storage/postgres/adapter.ts:1937`), so these checkpoints run one at a time even though rooms close in parallel **(inferred)**.
- **Updates still in the 5 ms grouping window are not committed by `close`.** It clears the timer (`apps/server/src/plan/service.ts:2406`) that `schedule` set (`:1718-1724`) and, unlike `drain` (`:1322-1328`), does not commit. Those updates were never acknowledged, so the browser replays them from its outbox after reconnecting (`packages/editor/src/provider.ts:421-426`) **(inferred)**.

### The writer lease

- The lease timing is TTL 30 s, renewal every 10 s, a 5 s safety margin and a 1 s retry (`apps/server/src/main.ts:178-181`).
- `WriterLease` renews on an interval (`apps/server/src/storage/writer-lease.ts:46-49`) and retries a failed renewal (`:76-87`). It calls `lost` at `renewedAt + ttl - safety` (`:98`), which is wired to `signal()` (`apps/server/src/main.ts:189-194`).
- `#acquire` inserts the row or takes it `FOR UPDATE` if it is expired or already this owner's, incrementing `fencing` (`apps/server/src/storage/postgres/adapter.ts:1830-1861`).
- `#renew` runs on its own one-connection pool with statement, lock and idle timeouts (`apps/server/src/storage/postgres/adapter.ts:479-512`, `:1863-1918`).
- `#assertLease` runs inside every fenced write. It takes an advisory lock keyed by the lease name, holds the row `FOR KEY SHARE`, and requires a matching owner, fencing value and unexpired expiry (`apps/server/src/storage/postgres/adapter.ts:1932-1954`). Jobs and research also take a fixed global advisory lock (`:559-565`, `:570-574`).
- Every writer reads the lease through a closure over the one process lease (`apps/server/src/main.ts:311-314`, `:2526`, `:2612`, `:2636`, `:2646`, `:2699`, `:2758`). A persistence failure in any single document calls `signal()` and drains the whole process (`apps/server/src/main.ts:315-318`).
- [Storage](storage.md) already says this lease "is why the current deployment model cannot perform a rolling application replacement" (`docs/storage.md:309-311`).

### What a restart does to logins

`docs/self-hosting.md:22-23` says a restart signs every browser out. **The code says otherwise for hosted mode.**

- **Hosted credentials persist.** Hosted mode passes encryption settings to `Sessions` (`apps/server/src/auth/routes.ts:182-188`), which stores an encrypted credential with each session (`apps/server/src/auth/session.ts:274-275`; columns from `apps/server/src/storage/postgres/migrations/016_persistent_sessions.sql:1-12`).
- **Restore is lazy.** A process that does not hold a session restores it from the row on its first authenticated request (`apps/server/src/auth/session.ts:380-395`, `:397-455`).
- **The startup reset keeps encrypted rows.** It deletes only rows with no credential, or expired ones (`apps/server/src/storage/postgres/adapter.ts:677-681`). It clears the Planner owner of **every** document and sets its status `unavailable` (`:672-676`).
- **Tests assert this.** `apps/server/src/storage/postgres/startup.test.ts:147-158` asserts it. `e2e/auth-lifecycle.e2e.ts:92-140` asserts that the same `/api/session` JSON and cookie survive a SIGTERM and a new server.

**What is true:** a hosted browser stays signed in across a restart as long as the database, `SESSION_ENCRYPTION_KEY`, origin and GitHub App client ID are stable (`docs/authentication.md:417-420`). A restart does lose the following:

- **Planner ownership** for every document. Under `copilot-sdk` and `atomic`, the next eligible turn claims it again. Until then, jobs that need the Planner's credential pause as `owner-unavailable` (`docs/background-jobs.md:484-488`).
- **Lookups of a live login by user ID.** These read memory only (`apps/server/src/auth/session.ts:466-473`). A remote Planner attach needs one, so the attach is refused until that person's browser has made a request to the new process (`apps/server/src/harness/remote/attachments.ts:545-551`). Restoring by session or user ID alone is deliberately not allowed (`docs/authentication.md:395-396`).
- **Local-mode sessions.** These are metadata-only, so the browser gets a new session through its binding cookie (`docs/self-hosting.md:25-27`). An in-progress device-flow attempt is held in memory (`apps/server/src/auth/local.ts:89-99`), so a restart loses it **(inferred)**.
- **A refresh caught between GitHub's rotation and the database commit**, which may require a new sign-in (`docs/authentication.md:407-409`).

`AGENTS.md:115-117`, `docs/authentication.md:393-396` and `docs/architecture.md:215-217` agree with the code. Three documents contradict it; see [Corrections](#corrections-to-existing-docs-found-while-researching).

### Planner sessions, attachments and harness state

- Under `HARNESS=remote`, attachments, holds and pending attaches are in-memory maps (`apps/server/src/harness/remote/attachments.ts:162-163`). `AGENTS.md:170-172` and [Agent connection](agent-connection.md#after-a-server-restart) (`docs/agent-connection.md:1023-1040`) say it plainly: "A server restart, graceful or not, forgets the sessions (a client's `resume` finds nothing)". Decisions stay open, and run cards come back stopped.
- A paired machine's Planner backend attaches with a `chopin_p_` credential, which `MachinePlanners` keeps only in memory (`apps/server/src/harness/remote/machine-planners.ts:42`, `:66-70`). After a restart the backend's credential is refused with 401 until the connector renews it (see [Stage 1](#what-changes-by-package)).
- A dropped link that offered `resumable-sessions` keeps its sessions only while the same process lives (`apps/server/src/harness/remote/link.ts:1052-1061`). With no earlier link, `resume` answers `resumed` with an empty list (`:1161-1171`).
- `close(code)` treats every code except `LINK_CLOSE.unresponsive` as planned (`apps/server/src/harness/remote/link.ts:1038`).
- `shutdownHarnesses()` clears credentials, shuts the adapter down and forgets Atomic workspaces (`apps/server/src/harness/harnesses.ts:143-148`).
- Under `atomic`, a live workflow run comes back stopped (`docs/hosted-agent.md:854-855`). Its journal lives under `$XDG_STATE_HOME/chopin` (`docs/hosted-agent.md:875`). The image says to mount a volume there (`Dockerfile:45-50`), but `compose.yaml` mounts none for the app.

### Rooms, presence, Chat and the browser outbox

- A room is an authoritative Y.Doc held in the process. An empty room is evicted after 30 s (`apps/server/src/main.ts:177`, `:1001-1010`). Presence is an in-memory Awareness (`apps/server/src/plan/presence.ts:65-71`). Child rooms record their parent (`apps/server/src/main.ts:2521`), and a child's Chat runs on its root's.
- The epoch is durable, so a reopened document keeps it (`apps/server/src/plan/service.ts:1422-1476`). `greet` honours the client's state vector only for the same epoch (`:1645-1663`), and `submit` silently drops an update from another epoch (`:1675-1680`). Edits are committed before `plan:ack` and relay (`:1846-1881`).
- The editor's outbox keeps every update until `plan:ack` (`packages/editor/src/provider.ts:132`). It is bounded by merging, not trimming (`:88-89`). After reconnecting, `resume()` reopens with the epoch and state vector and replays the outbox (`:260-272`, `:349-392`). A different epoch discards local state as `replaced` (`:364-367`, `:571-582`). A server restart therefore loses no acknowledged or queued edit as long as the epoch is unchanged **(inferred)**. No test exercises this with a real restart.

### Open tabs and front-end assets

- Reconnect uses exponential backoff with jitter: `min(500·2^n, 15000) × (0.5 + random)`, with the first attempt guaranteed by 1.2 s (`apps/web/src/wire.ts:57-68`, `:263-267`). There is no attempt limit. Focus and visibility wake a waiting timer at most once a second, and only `online` resets the backoff, because "a deploy outage must not turn every tab switch on every client into a fresh run of fast retries" (`:133-142`).
- Before each retry the client probes the endpoint (`apps/web/src/wire.ts:235-250`). **Any 4xx answer is taken as a refusal and the tab stops retrying** (`:240-246`, `:258-260`). A 401 reloads the page (`apps/web/src/room-workspace.tsx:1164`). If the hosted proxy answers 4xx while no upstream exists, every open tab would stop reconnecting **(inferred)**; it depends on the proxy.
- The notice stays silent for 1.5 s, shows "Reconnecting…", and then shows "Offline" after a further 5 s (`packages/editor/src/connection-notice.ts:6-8`, `:17-20`; labels at `packages/editor/src/status.tsx:57-74`).
- The browser wire has no protocol or build version. `session:hello` carries only capability booleans (`packages/protocol/index.d.ts:65-83`). The client ignores frame kinds it does not know (`apps/web/src/wire.ts:305`). No "updating" or "new version" state exists.
- Built files come from `apps/web/dist` (`apps/server/src/main.ts:169`, `Dockerfile:61`). Hashed `/assets/*-xxxxxxxx.*` files are immutable for a year (`apps/server/src/client.ts:33-35`). **Any missing path, including an old build's chunk, gets `index.html` with status 200** (`apps/server/src/client.ts:99-101`). A lazy import of the room workspace is retried on the next call (`apps/web/src/document-workspace-host.tsx:31-39`). Nothing handles Vite's `vite:preloadError`. After a deploy, an open tab that loads a not-yet-loaded chunk receives HTML for a module **(inferred)**; this was not run in a browser.

### MCP, connectors and agent connections

- **MCP.** The `/mcp` handler calls itself stateless (`apps/server/src/mcp.ts:972`) but keeps an in-memory session map (`:981`), minted by `initialize` (`:1014-1017`). After a restart an old `mcp-session-id` is unknown. Most tools still work, but the implementation lifecycle tools answer `session-required` (`:1283-1284`, `:1311-1312`). The hourly limit on automatic `invoke_planner` follow-ups is also per process (`apps/server/src/main.ts:203`, `apps/server/src/mcp/invoke.ts:36-44`).
- **Connector connections.** These are in-memory maps of connections, tokens and run tokens (`apps/server/src/experiments/connections.ts:130-140`), forgotten 90 s after last contact (`:83`).
- **Builds already survive a restart.**
  - The server waits `RESUME_MS = 600_000` for the machine and then gives it `RECONNECTED_MS = 60_000` to carry the build on (`apps/server/src/tasks/connector.ts:42`, `:48`, `:187-202`). `CHOPIN_BUILD_RESUME_MS` overrides the first value (`apps/server/src/config.ts:314`).
  - The connector keeps an agent running for `RUN_GRACE_MS = 600_000` without reaching Chopin (`apps/connector/src/reconnect.ts:62`), with its heartbeat retrying (`apps/connector/src/run.ts:155-172`).
  - `e2e/build-restart.e2e.ts:209` covers this. The run credential is described as derived from `SESSION_ENCRYPTION_KEY` (`docs/local-experiments.md:224-227`); that code was not traced.
- **Connector reconnect.** The connector uses full jitter capped at 5 minutes and resets the ladder after a connection has been healthy for 60 s (`apps/connector/src/reconnect.ts:5-13`, `:45`). Its first retry after a working connection drops is immediate (`apps/connector/src/connection.ts:276-301`).
  - A 5xx, 408, 429, timeout or network error is retried. **Any other 4xx except 401 stops the connector** (`apps/connector/src/machine.ts:475-505`, rule at `:504`), so a proxy 404 during a deploy would stop it **(inferred)**.
- **Connector versions.** Every connector request carries its version and protocol (`packages/protocol/connector.ts:5-6`). The connector speaks protocol 6 (`apps/connector/src/version.ts:9`). The server accepts `{ min: 2, max: 6 }` (`apps/server/src/experiments/routes.ts:232`). Anything else gets HTTP 409 `connector-update-required` naming `chopin update <version>` (`:270-302`, status at `:1246`). `GET /api/connector/version` publishes the range (`:1252-1253`).
- **`chopin update` interrupts work.** It restarts a running service at once (`apps/connector/src/service.ts:1435-1464`), and the connector's SIGTERM handler reports running work as stopped (`apps/connector/src/main.ts:568-575`).
- **Agent connections.** The subprotocol is the version, and additive changes are features (`packages/agent-link/src/protocol.ts:7`, `:12-16`, `:23-42`; `docs/agent-connection.md:87-93`). The package client ignores a server message type it does not know, because its `serve` switch has no default (`packages/agent-link/src/client.ts:399-490`). It ends the link only on a frame that is not a JSON object with a string `type` (`:174-184`, `:594-602`). The protocol does not require other clients to ignore unknown types, and it expects some clients to validate strictly (`docs/agent-connection.md:105-110`), so a new server message type belongs behind a feature. The document is named in `attach` after the upgrade (`packages/agent-link/src/client.ts:560-566`), not in the URL.

### Health and tests

- The only health signal is `GET /api/session` (`apps/server/src/auth/routes.ts:424`). Without a cookie it returns early (`apps/server/src/auth/session.ts:331-333`), so the image health check (`Dockerfile:70-71`) proves only that the process answers HTTP. The image health check "does not prove that a browser bundle is present, a new database transaction can complete, GitHub is reachable, or the Planner can start" (`docs/self-hosting.md:699-701`).
- **No test restarts the real server while a tab stays open and edits through it.** Reconnect tests close the browser's socket with `page.routeWebSocket` (`e2e/connection.e2e.ts:1-6`). The build restart test reloads the page after the restart (`e2e/build-restart.e2e.ts:257`).

## Reference review

Each source below was opened for this document, and the quotes were re-checked against the live page on 2026-11-05.

**Drain and reconnect.**

- [Discord's gateway](https://discord.com/developers/docs/events/gateway) resumes a dropped session from a session ID and the last sequence number, replaying missed events. A client that ignores the `resume_gateway_url` "will experience disconnects at a higher rate than normal". The server can send a Reconnect event before closing. _Decision here:_ a deliberate restart should tell clients to come back and keep the state they need to resume, which for Chopin means the document epoch and outbox, already durable, plus Planner link state, which is not.
- The [websocket.org reconnection guide](https://websocket.org/guides/reconnection/) lists "Server deploys — rolling restarts close active connections" as a common cause of drops and recommends exponential backoff with jitter, starting at 500 ms and capped at 30 s. It warns that sticky routing "breaks on the most common reconnection scenario" and that a client should stop after a bounded time and show the state. _Decision here:_ keep `wire.ts`'s jittered backoff, which already matches. Add a deliberate-restart path, not a new loop.
- Kubernetes' [pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) and [termination tutorial](https://kubernetes.io/docs/tutorials/services/pods-and-endpoint-termination-flow/) describe SIGTERM with a grace period. Endpoint removal runs in parallel, and terminating endpoints are reported not ready. A third-party guide, [Draining WebSocket connections during deploys](https://www.real-time-websocket.com/scaling-real-time-infrastructure/horizontal-scaling-kubernetes/draining-websocket-connections-during-deploys/), adds: flip readiness first, close sockets with an explicit code in staggered batches, and note that a process exiting without closing leaves clients seeing 1006, "indistinguishable from a network failure". _Decision here:_ separate liveness from readiness and close with an explicit restart code. Readiness is failed at the cut, not at SIGTERM: the old process keeps serving through its turn wait, turns readiness off only when little work is left, and keeps serving until the proxy has seen that, so a request routed to it in between is served rather than refused (see [Hand-over sequence](#hand-over-sequence)).
- The [IANA WebSocket close code registry](https://www.iana.org/assignments/websocket/websocket.xml) lists 1001 "Going Away" (RFC 6455) and 1012 "Service Restart". _Decision here:_ send 1012, which says what happened, rather than relying on Bun's 1001. Chopin's agent links already use 1001 to mean an unresponsive client.

**One owner per document.**

- Figma's [How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/) runs "a separate process for each multiplayer document which everyone editing that document connects to". A reconnecting client downloads a fresh copy and reapplies its offline edits.
- Figma's [Making multiplayer more reliable](https://www.figma.com/blog/making-multiplayer-more-reliable/) explains that with a journal, a deploy only has "to close all connections and wait for any unsaved changes to be persisted in the journal". Checkpoints after a close are deferred with jitter so a deploy does not spike database writes. Ownership is a lock row whose UUID conditions every journal write, and clients of one file must reach the instance that holds it, or "we'd get into 'split brain'". _Decision here:_ Chopin already commits every edit before acknowledging it, so a drain need not checkpoint every room, and a fenced per-document lease is the proven shape for several processes.
- Hocuspocus's [scalability guide](https://tiptap.dev/docs/hocuspocus/guides/scalability) suggests, for CPU or memory pressure, "multiple independent Hocuspocus instances and split users by a document identifier". Its [Redis extension](https://tiptap.dev/docs/hocuspocus/server/extensions/redis) instead fans every update out to every instance: "all messages will be handled on all instances … if you are trying to reduce cpu load … you should not connect them via Redis."
- Docmost's [server-affinity extension (PR #1873)](https://github.com/docmost/docmost/pull/1873) "ensures the Yjs document state is owned and loaded by a single server, while other servers proxy requests to it". _Decision here:_ compare ownership against fan-out and sticky routing in [Approaches considered](#approaches-considered).

**Expand and contract.**

- Prisma's [expand and contract guide](https://www.prisma.io/dataguide/types/relational/expand-and-contract-pattern) moves data "from an old data structure to a new data structure without affecting uptime", and allows rollback "at most points in the process".
- Stripe's [Online migrations at scale](https://stripe.com/blog/online-migrations) dual-writes, moves reads, moves writes, then removes the old data, copying lazily.

_Decision here:_ during a hand-over or a rollback, two Chopin versions read one schema and one sidecar JSON format. Both must therefore change in separate expand and contract releases, and CI must prove it.

**Staging, canary, rollback and feature flags.**

- Google's SRE workbook chapter on [canarying releases](https://sre.google/workbook/canarying-releases/) says that if the canary's error rate is too far from the control's, "we should pause and roll back the deployment". It describes blue/green cutover as needing no downtime, with "rollback … a trivial reversal of the router change", at "twice as many resources". It recommends feature-flag frameworks to "separate feature launches from binary releases".
- Kubernetes [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) stop a bad rollout but roll back only by hand.
- A Docker Compose [healthcheck](https://docs.docker.com/reference/compose-file/services/) reports health and gates dependent services. It does not roll back.

_Decision here:_ automatic rollback is deployment tooling outside this repository, and it is only safe if the previous image can run against the new schema.

**Proxy hold and retry.** Caddy's [`reverse_proxy`](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) can "hold requests until a healthy upstream can be selected (e.g. to wait and mitigate errors while rebooting or redeploying an upstream)" with `lb_try_duration`; the docs suggest 5 s as a starting point. A failed dial is always retried, but by default "only GET requests are retried" once a connection to the upstream has succeeded. Reading Caddy's source for the reference sheet behind this document, a WebSocket is retried only until the upstream answers 101 and never afterwards. That was not tested against a live server. _Decision here:_ proxy retry can cover a short gap for new connections, including WebSocket handshakes. It cannot move an established socket, and its settings belong to whoever runs the proxy.

**Leases and pooling.**

- PostgreSQL's [advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html) end with their session or transaction.
- PgBouncer's [feature table](https://www.pgbouncer.org/features.html) marks session-level advisory locks and LISTEN as "Never" under transaction pooling.

_Decision here:_ keep using lease rows with fencing and transaction-scoped advisory locks, which Chopin already does, and do not depend on LISTEN or session locks without knowing the pooler.

**Protocol facts used below.**

- The MCP [Streamable HTTP transport](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports), the version Chopin answers (`apps/server/src/mcp.ts:1019`), says a server that ended a session "MUST respond to requests containing that session ID with HTTP 404". A client receiving that "MUST start a new session".
- Vite's [build guide](https://vite.dev/guide/build#load-error-handling) emits `vite:preloadError` when a dynamic import fails. It describes exactly the case of a deploy deleting old chunks, with `Cache-Control: no-cache` on the HTML.

## Chosen design

### Stage 1: invisible restarts on one server

The outcome: a deploy is strictly invisible. No notice appears within the 1.5 s reconnect grace, and a remote Planner that resumes within its hand-over window is never shown as disconnected. A request that reaches the proxy during the hand-over is held there and then served by one of the two processes, never refused. The one exception is a request still running in the old process when its in-flight bound runs out at the cut (step 3.5.3 below). This needs two processes to overlap on one database. The new one starts, migrates, warms and waits beside the old one, and takes the writer lease the moment the old one releases it. Only the lease holder serves, so the single-writer rule holds at every moment. Two remote-Planner cases are bounded exceptions, listed in open question 3 (h): an owner whose browser login cannot come back within the window, and an agent client that does not resume within it.

#### Hand-over sequence

1. **The new process starts beside the old one, warm but not serving.**
   - It runs migrations, which in this stage must be expand-only; see [Stage 2](#stage-2-release-safety) for how that is checked.
   - It loads the configuration, verifies the schema (`apps/server/src/main.ts:2897`, `storage.health()`) and opens its listener in **standby**. Warm-up is limited to pools, the schema check, static files and caches that write nothing. It starts no Planner harness and no turn.
   - `GET /api/health/live` returns 200 with the status word `standby`. `GET /api/health/ready` returns 503, so no proxy routes to it. Static files are served at once. Other requests and WebSocket upgrades are held up to a bound such as 20 s, then answered with 503 and `Retry-After`. That is the fallback for a proxy that cannot hold requests. The socket upgrade already awaits admission before `upgrade()` (`apps/server/src/main.ts:1781-1789`), so holding there is feasible **(inferred)**.
2. **The new process waits for the lease without writing.**
   - It polls the `chopin:writer` row with a plain read every 100 ms, and calls the locking `#acquire` only once the row shows the lease released or expired. Polling therefore never queues `FOR UPDATE` behind the holder's `FOR KEY SHARE` writes (lock modes at `apps/server/src/storage/postgres/adapter.ts:1842-1844`, `:1938-1943`) **(inferred)**. One single-row read every 100 ms is a small load.
   - It arms no renewal or deadline until it acquires. `writerLease.hold` and `writerLease.start()` run only after the acquisition (`apps/server/src/main.ts:2912`, `:2942`).
   - LISTEN/NOTIFY would be faster, but depends on the pooler; see [Open questions](#open-questions).
3. **The platform sends SIGTERM to the old process only after the new one is warm.** The old process then does the following:
   1. It keeps readiness on and keeps serving every request and open socket until its cut. Readiness is not turned off at SIGTERM, because a proxy would then hold every new connection through the whole turn wait. From SIGTERM on, every HTTP answer carries `Connection: close`, so the proxy keeps no idle connection to the old process by the time the cut begins. Whether Bun honours that header on every route is for the restart test to check **(inferred)**.
   2. It stops starting new Planner turns. An acknowledged Planner request is durable before it is acknowledged, in normal operation and not only during a drain. A request that cannot start at once is recorded as a `waiting` row in the same fenced transaction, before its acknowledgement. That covers a Chat message, a comment note sent to Chopin, a task draft from Build and an `invoke_planner` call; [Deferred Planner turns](#deferred-planner-turns) lists every kind of queued turn and what happens to each. After SIGTERM that is every new Planner request, and each is acknowledged as queued. A request already queued behind a running turn before SIGTERM is covered the same way. Today such a request is acknowledged from memory only (`apps/server/src/chat/service.ts:1013-1025`, `:1146-1154`) and dropped when `Chat.close` clears the queue (`apps/server/src/chat/service.ts:3102-3111`). A turn that never started is not a replay.
   3. It lets running turns finish while it keeps serving, up to `HANDOVER_TURN_WAIT_MS`. No socket closes during this wait, so the wait is invisible. A turn still running at the limit is aborted as today and never replayed. A Chat notice says that it was interrupted, and a turn that started from a deferred row has that row marked `interrupted` in the same transaction.
   4. It commits and checkpoints every room while still serving, through `Service.drain` (`apps/server/src/plan/service.ts:1322-1328`), and stops the job runner and harnesses. This work runs before the cut, so the cut has little left to do.
   5. **The cut.** Its steps run in this order, so that the old process never answers a request after it releases the lease:
      1. Readiness turns off (`ready` answers 503) while the process still holds the lease and still serves every request and socket. It then waits a fixed unready window, `HANDOVER_UNREADY_MS`, before the next step. A process cannot know how many proxies check it, so it does not count them: the operator sets the window to the proxy's health interval plus a margin, 300 ms for the reference (250 ms plus 50 ms). It always waits the whole window and never longer. It logs how many readiness checks it answered with 503 in the window. Zero means no proxy checks readiness actively, for example one with only passive health checks, so requests may still reach the listener the next step stops. The hand-over then goes on, the log line counts it as a budget risk, and the deploy-under-load test must show whether it caused a failed request or a notice. The process never waits for a check that may not come, so the drain never runs into the kill. A request the proxy routes to it during the window is served, not refused. Once an active proxy has seen the 503, it has no ready upstream, so it holds new requests.
      2. It stops its listener without closing sockets, as `server.stop(false)` does (see [Drain order](#drain-order)). The proxy no longer chooses it, so no connection is being opened to it. A dial that still arrives is refused at the transport level, and Caddy retries a refused dial for every method (see [Reference review](#reference-review)).
      3. It finishes the HTTP requests already in flight, under the lease it still holds, for up to `HANDOVER_REQUEST_WAIT_MS` (proposed: 1 s). A held connector poll (`apps/server/src/experiments/connections.ts:668-693`) is woken and gets its ordinary empty answer. A request still running at the bound is the one exception to the outcome above: its connection is closed without an answer. Caddy retries it only if it is a GET, and any other method gets Caddy's 502. Each such request is logged.
      4. It stops admitting edits, commits the residual batches, persists remote Planner link state, and releases the lease (`apps/server/src/storage/postgres/adapter.ts:1920-1930`). For each hold whose link is still live at this point, the persisted hold records `handover_until`, the release time plus `HANDOVER_PLANNER_WINDOW_MS` (proposed: 10 s; see [Remote Planner budget](#remote-planner-budget)). Edits sent after this point are not acknowledged and stay in the browser outbox (`packages/editor/src/provider.ts:132`).
      5. It sends `session:restarting` where negotiated, and `restarting` with `reconnectWithinMs` to agent links that offered `restart-notice`, closes each socket and link with 1012, and exits 0. It publishes no Planner status for the links its own cut closes. Today `announcePlanner` already broadcasts nothing once `draining` is set (`apps/server/src/main.ts:985-993`, set at `:1873`); stage 1 keeps announcing real attaches and drops through the turn wait, and stops only at the cut. Only now does a client lose its connection, so each client's 1.5 s grace starts here.
4. **The new process acquires the lease within about 100 ms of the release.** It runs the narrowed startup reset and the other lease-bound steps, rebuilds the persisted holds, and becomes route-ready (`/api/health/ready` returns 200). A hold whose `handover_until` is still ahead is presented as attached until then (see [Remote Planner budget](#remote-planner-budget)). The proxy's next health check adopts the process, and the requests the proxy held then reach it. Deferred Planner turns start only after route-ready, off the readiness path. The process then loads the `planner_deferred_turns` rows, marks stale `started` rows `interrupted`, and starts `waiting` rows under the [start rule](#deferred-planner-turns). Readiness never waits on this work.

Budget, measured from the release, which is when clients lose their sockets. These are design targets for the restart test, not measurements:

- the waiting process sees the release: within 100 ms, the poll interval;
- lease-bound startup (reset, child-conversation clearing, experiment recovery): within 300 ms, or those steps move behind readiness where they cannot fit (`apps/server/src/main.ts:2921-2948`) **(inferred)**;
- the proxy's active health check adopts the new process: within 250 ms, the reference health interval;
- a request the proxy holds is tried again: within 100 ms, the reference `lb_try_interval` (Caddy's default is 250 ms).

Summed worst case: about 750 ms from the loss until the proxy serves held requests from the new process. The proxy's hold before the release also includes the cut's first steps, at most about 300 ms plus the in-flight requests. That delays held HTTP requests but starts no client's grace.

The browser sets a tighter limit than 1.5 s. On a loss it first sends its probe (`apps/web/src/wire.ts:235-250`, awaited at `:256`), which the proxy holds until it adopts the new process. The browser then waits 250 to 750 ms before its attempt, but no later than 1.2 s after the loss (`RESCUE_AT`, `apps/web/src/wire.ts:68`, `:263-267`). It counts as connected when the socket opens (`apps/web/src/wire.ts:199-204`). So:

- if the proxy adopts the new process within 1.2 s of the loss, the attempt starts by 1.2 s, and its upgrade and admission must finish within the last 300 ms of the grace;
- if adoption comes later, the attempt starts 250 to 750 ms after adoption, and a notice is likely.

That leaves two margins. Adoption has about 450 ms of slack (750 ms against 1.2 s). The upgrade has about 300 ms, and that margin is thin. Every attempt whose wait `RESCUE_AT` cuts short starts at 1.2 s, at the same moment as the others. Each lands on a process that restores each login from the database on its first request (`apps/server/src/auth/session.ts:380-399`). The restart and load tests must measure upgrade latency at that moment. With Caddy's 500 ms health interval and default 250 ms `lb_try_interval`, adoption could take about 1.15 s and leave almost no slack. The reference therefore uses 250 ms and 100 ms.

Fallback. A hand-over that misses either limit shows today's "Reconnecting…" notice at 1.5 s (`packages/editor/src/connection-notice.ts:6`) and logs the measured gap. The design allows no planned miss. The release test counts zero notices, and every production miss is logged and investigated as a defect. The upgrade margin is thin, so the expected cause of a miss is a burst of reconnects at the 1.2 s point. Strict invisibility is therefore switched on only after the load test shows zero notices at a production-like number of clients. The outbox keeps every unacknowledged edit either way.

If the platform cannot start the replacement before stopping the old process, step 1 happens after the cut. The gap then includes the whole boot, and no budget can be met without a proxy that holds requests. Strict invisibility therefore needs the overlap that the [reference deployment](#reference-deployment) shows.

#### Remote Planner budget

Under `HARNESS=remote`, browsers learn the Planner's state from `session:planner`, sent after `Hello` and on every change (`apps/server/src/main.ts:1716-1717`, `packages/protocol/index.d.ts:117-122`). `status()` reports a hold whose link dropped with its work kept as `disconnected` (`apps/server/src/harness/remote/attachments.ts:284-294`). The browser treats every state except `attached` as detached: Build plan reads "Agent offline" with the tooltip "Local agent disconnected", and Planner comments are no longer offered (`apps/web/src/room-workspace.tsx:712-715`, `:1566`; `apps/web/src/build-plan-button.tsx:520-548`). A later `@chopin` message, comment note or task draft is refused with `planner-not-attached`, whose message says that the Planner is disconnected (`apps/server/src/main.ts:628-641`, `:946-949`; `apps/server/src/comments/service.ts:351-353`; `apps/server/src/chat/service.ts:1247-1249`). Rebuilding the holds as suspended would therefore show every member of a remote-Planner document a disconnected Planner after each deploy, at least until its client resumes. The resume itself needs the owner's login, which is restored only when the owner's browser sends its cookie. Stage 1 therefore adds a hand-over window:

- **Window.** At the cut, each hold whose link is still live records `handover_until`, the release time plus `HANDOVER_PLANNER_WINDOW_MS` (proposed: 10 s). A hold that was already disconnected, or within its grace period, keeps its state, because the deploy did not cause it.
- **Presentation.** Until `handover_until`, `status()` reports the rebuilt hold as `attached` with its login, as it already does for a hold that has neither a link nor a grace deadline (`apps/server/src/harness/remote/attachments.ts:288-291`). `holding()` reports it attached for its owner's own views (`apps/server/src/harness/remote/attachments.ts:240-262`). The run cards of its sessions stay live and unmarked. Today `restoreRuns` stops every live card when a room is reopened, because no session survived (`apps/server/src/chat/service.ts:1543-1546`, used at `:363`). A card whose session a rebuilt hold keeps is restored live instead, and gets the `disconnected` mark only after the window (`apps/server/src/chat/service.ts:1535-1541`).
- **Requests in the window.** `plannerNotAttached` (`apps/server/src/main.ts:628-641`) accepts a request for a rebuilt hold within its window. A `@chopin` message, comment note, task draft or `invoke_planner` call is then acknowledged as queued and recorded as a `waiting` row. `invoke` resolves the owner when it accepts a call (`apps/server/src/chat/service.ts:787-790`); for such a hold that check moves to the row's start, as for every row. The rows start once the client resumes, under the `HARNESS=remote` [start rule](#deferred-planner-turns). Server-authored turns still wait for a live link, as today (`apps/server/src/main.ts:343-345`, `:388-399`).
- **Resumed in time.** A `resume` that takes the hold back before `handover_until` binds it as an attach does today (`apps/server/src/harness/remote/attachments.ts:593-611`), ends the window and starts the queued rows. Members saw no change.
- **Missed.** When the window ends without a resume, the hold becomes `disconnected`, as a dropped link is today. That change is announced, and the hand-over logs it as a remote-Planner miss with its cause: the owner's login was not back, or the client was not. Requests accepted in the window stay `waiting`, with the notice that they wait for the Planner to reconnect. New requests are refused with `planner-not-attached`, as today.

The agent client's budget, from the release:

- the proxy adopts the new process within about 750 ms (the budget above). A client that offered `restart-notice` reconnects at once on the 1012 close, and the proxy holds its upgrade until then;
- the owner's login is restored when the owner's browser reconnects, by about 1.5 s for an open tab (`apps/web/src/wire.ts:263-267`; restore at `apps/server/src/auth/session.ts:380-399`). A `resume` before that is refused with `unavailable` and `retry: true`;
- the client retries the refused `resume`. Today it does so on its own backoff, which Chopin does not set (`docs/agent-connection.md:346-349`), and this repository ships no first-party backend (`docs/agent-connection.md:1177-1180`). The `restart-notice` feature therefore adds a client rule: after `restarting`, a client retries a `resume` refused with `retry` every 250 ms until `reconnectWithinMs` has passed, then returns to its own backoff. `reconnectWithinMs` is the window.

That is about 2 s for a client that follows the rule and an owner with a tab open, against a proposed 10 s window. The window also bounds how long a Planner that is not coming back is shown as attached. Requests sent in that time are durable rows, so nothing is lost. A browser may throttle timers in a hidden tab **(inferred)**, so the owner's login can come back later than 1.5 s, and the restart test must measure the window with the owner's tab hidden. The window's value is a proposal to measure, like the other timings.

#### What changes, by package

- **`apps/server` `main.ts`:**
  - Split startup into boot, standby, acquire, lease-bound startup and serve. The fail-fast at `apps/server/src/main.ts:2911` becomes the wait, behind `HANDOVER=wait`.
  - Two readiness states. **Warm** (standby): the listener is open, the schema is verified, and `live` returns `standby`. **Route-ready**: the process holds the lease, the lease-bound startup is done, a database transaction completes, and `apps/web/dist/index.html` exists. Only route-ready answers `ready` with 200. Readiness requires the lease, and the holder turns it off at the start of its cut while it still serves. So at most one process is ready at a time, by construction.
  - Reorder `drain()` (`apps/server/src/main.ts:1872-1929`) as in the hand-over sequence. The turn wait and pre-cut commits run while serving. The cut then runs in its fixed order: readiness off for the fixed `HANDOVER_UNREADY_MS` window, listener stopped without closing sockets, in-flight requests finished, lease released, sockets and links closed with 1012. The drain deadline is shorter than the platform's stop grace, with a margin.
  - Keep announcing Planner status changes until the cut, and suppress them from the cut on, instead of from the start of `drain()` as today (`apps/server/src/main.ts:985-993`).
  - From SIGTERM, answer every HTTP request with `Connection: close`.
  - Add `GET /api/health/live` and `GET /api/health/ready`, both unauthenticated and returning only a status word. The Docker `HEALTHCHECK` (`Dockerfile:70-71`) moves to `live`.
  - Startup work after the lease, the reset included, must fit the budget. Child-conversation clearing (`apps/server/src/main.ts:2923`) and experiment recovery (`apps/server/src/main.ts:2948`) move behind readiness if they cannot (**inferred**; to be measured).
- **`apps/server` lease and storage:**
  - Add a non-locking `leases.peek(name)` to the storage port and both adapters.
  - Narrow `sessions.reset` (`apps/server/src/storage/postgres/adapter.ts:668-692`) so it keeps the owner reference of a document with a persisted suspended remote Planner hold. Deferred turns need no such exception, because their row carries its own claimant.
  - The writer lease itself is unchanged. The holder renews every 10 s against a 30 s TTL, with a 5 s safety deadline (`apps/server/src/main.ts:178-181`, `apps/server/src/storage/writer-lease.ts:98`), so the old process keeps renewing through its turn wait.
- **`apps/server` auth:**
  - The old process must not start a GitHub token refresh after SIGTERM. Refresh tokens are single-use (`docs/authentication.md:381-383`, `:400-401`), so a refresh racing the new process's restore of the same login could revoke it (`apps/server/src/auth/session.ts:689-692`) **(inferred)**.
  - Local mode (`AUTH_MODE=local`) keeps today's behaviour. It is loopback-only and never handed over.
- **`apps/server` harness/remote:**
  - Persist each resumable link's held sessions, waited-on request IDs, owed answers and held stops when the link drops, when it is suspended (`apps/server/src/harness/remote/link.ts:1052-1061`), and on shutdown. This is the decision recorded in open question 4.
  - On start, rebuild holds as suspended, so a returning client's `resume` (`apps/server/src/harness/remote/link.ts:1161-1171`) takes them back. A hold whose link the cut closed carries `handover_until`, and is presented and admitted as described in [Remote Planner budget](#remote-planner-budget): `status()`, `holding()` and `plannerNotAttached` treat it as attached until then, `restoreRuns` keeps its sessions' cards live, and a timer turns it `disconnected` when the window ends without a resume.
  - The owner login is still needed, and it is restored only from its browser cookie (`docs/authentication.md:395-396`, unchanged). Until the owner's browser sends its cookie, a returning client's `resume` must be answered `refused` with code `unavailable` and `retry: true`, which clients retry (`docs/agent-connection.md:1010-1011`). Today `resume` never looks at the login (`apps/server/src/harness/remote/link.ts:1161-1171`). The check sits in attach, which refuses with `sign-in-required` (`apps/server/src/harness/remote/attachments.ts:545-551`, `:746-753`). That code closes the link for good (`apps/server/src/harness/remote/link.ts:95`), so it must not be used here. `retry` is set only for `unavailable` (`apps/server/src/harness/remote/link.ts:1261`). This reuses an existing code for a new case; it adds no protocol element.
  - In hosted mode a paired machine's Planner needs no browser. Its login is created again from the machine's own GitHub grant, which is durable and encrypted (`apps/server/src/auth/machines.ts:55-56`, `:190-200`). Under `AUTH_MODE=local`, machines hold no grant and must borrow a browser sign-in (`apps/server/src/harness/remote/machine-planners.ts:124-127`), so local mode keeps today's behaviour. Its backend's `chopin_p_` credential is not durable. `MachinePlanners` keeps it only in memory (`apps/server/src/harness/remote/machine-planners.ts:42`, `:66-70`, `:95-99`), so after a restart `endpoint.ts` answers 401 (`apps/server/src/harness/remote/endpoint.ts:161-162`). The backend reads its token file on each refusal, but that file holds the connector's last credential, which the connector renews only on a timer, 5 minutes before the 15-minute lifetime ends (`apps/connector/src/planner-token.ts:5-10`, `:30-31`). Until then the persisted holds stay unreachable, for up to about 10 minutes.
  - **Remedy (a), chosen:** persist a digest of each credential when it is issued, as `planner_credentials` in the data model. The new process then accepts an unexpired credential at once. The connector and backend do not change, and nothing needs persisting at shutdown.
  - **Remedy (b), the alternative:** the connector requests a fresh credential for each running backend as soon as one of its own calls fails with `connection-unavailable` or `authentication-required`, the `forgotten` class (`apps/connector/src/machine.ts:454`, `:503`; `apps/server/src/experiments/connections.ts:354`). Connections live in memory, so that failure follows a restart, and `POST /api/connector/planner` authenticates the durable machine token (`apps/server/src/experiments/routes.ts:1503-1509`). This needs a connector change, whose compatibility with older connectors belongs with [Stage 4's support window](#support-window). It bounds the wait only by the connector's next call. A backend's 401 never reaches the connector, so an idle machine still waits for the timer.
- **`apps/server` chat and deferred turns:**
  - Record every acknowledged Planner request that does not start at once as a `planner_deferred_turns` row, in the same fenced transaction as the commit that precedes its acknowledgement. The kinds, listed with their code in [Deferred Planner turns](#deferred-planner-turns), are a composer `@chopin` message, an `invoke_planner` member message, an `invoke_planner` call with `as: "system"`, a comment note sent to Chopin in a root or a child document, and a task draft from Build. After SIGTERM that is every such request. It applies in normal operation as well as during a drain, so a crash loses no acknowledged request either. #### Data model

All of these tables are additive (expand) migrations.

- **`planner_link_holds`.** Columns: root document ID, user ID, login session ID or machine ID, session ID, `waiting` (request IDs, `jsonb`), `owed` (answers not yet acknowledged, `jsonb`), `stops` (held stops, `jsonb`), `suspended_at`, `handover_until` (nullable: the end of the hand-over window, set only for a hold whose link the cut closed; see [Remote Planner budget](#remote-planner-budget)), and the writer lease `fencing` it was written under.
  - Rows are deleted by everything that ends a hold today: detach, sign-out, reset, archiving and the rest listed at `docs/agent-connection.md:1012-1021`.
  - Whether owed answers can reuse the stored Decision-answer records (`apps/server/src/main.ts:1913`) needs a closer look.
- **`mcp_sessions`.** Columns: `id`, `user_id`, `client_name`, `client_version`, `created_at`, `last_seen_at`. Idle sessions are swept with the existing session cleanup (`apps/server/src/main.ts:2943-2944`). An unknown ID keeps today's answers. Answering 404 per the MCP specification would make conforming clients re-initialize, but it could break clients that ignore that rule, so it is left as an open question.
- **`planner_deferred_turns`.** One row per acknowledged Planner request whose turn did not start at once; [Deferred Planner turns](#deferred-planner-turns) lists the five kinds. A queued composer message has no transcript entry until its turn starts (`apps/server/src/chat/service.ts:2780-2797`), and the delivery fingerprints are one-way digests (`apps/server/src/chat/service.ts:79-83`). So the row carries everything the turn and a retry need, the fields of today's in-memory `Waiting` entry (`apps/server/src/chat/service.ts:98-127`) and of the `Instruction` it came from (`apps/server/src/chat/service.ts:159-188`):
  - `id`, `document_id` (the root), and `request_id`, unique: the ID the acknowledgement named. That is the composer's request ID, the member entry an `invoke_planner` call posted (`apps/server/src/chat/service.ts:803-808`), the draft ID (`apps/server/src/chat/service.ts:1254-1257`), or, for a system `invoke_planner` call and a comment note, the ID of the notice posted when it was accepted (`apps/server/src/chat/service.ts:1072-1077`);
  - `kind` (`composer`, `invoke_planner`, `invoke_system`, `comment` or `draft`), `handle`, `user_id`, `text` and `references` (`jsonb`), as `Wire.Waiting` and the queue entry hold them (`packages/protocol/chat.d.ts:235-240`). A `comment` row stores no text, because its prompt is built from the thread when it starts;
  - `delivery` (`jsonb`: destination plus request and canonical fingerprints), for a composer row, so `replay` recognises a retried send as it does today (`apps/server/src/chat/service.ts:508-547`);
  - `focus_channel_id` and `focus_title`, nullable: the child the member had open, which today lives only on the in-memory entry (`apps/server/src/chat/service.ts:121-122`, set at `:1013-1023`) and never on the persisted `MemberEntry` (`apps/server/src/chat/service.ts:85`);
  - `thread_id` and `thread_channel_id`, nullable, for a `comment` row: the thread, and the child holding it when it is not in the root, as `Instruction.thread` and `threadChannel` carry them today (`apps/server/src/chat/service.ts:166`, `:179-180`). At most one row per thread is `waiting`;
  - `plan_revision`, nullable, for a `draft` row: the revision Build asked for, as `TaskDraft` holds it (`apps/server/src/chat/service.ts:130-136`);
  - `claimant_session_id` and `owner_session_id_at_accept`: the sender's login session and the document's owner when the row was accepted (a row queued behind owner X's running turn records X), so either one coming back can claim after a deploy, as X would have run it without one. The sender's session is the entry's `sessionId` (`apps/server/src/chat/service.ts:110-111`, set for an instruction at `:1152`), which `resolveOwner` uses only to claim a document that has no owner (`apps/server/src/chat/service.ts:2299-2301`). Under `HARNESS=remote`, where only an attachment may claim (`apps/server/src/chat/service.ts:2282-2285`), it is recorded but never used to claim;
  - `state` (`waiting`, `started`, `ended`, `interrupted` or `cancelled`), `created_at`, `fencing` (the writer lease the latest transition was written under) and `resolved_at`.
  - The session ID is an identifier only: it cannot restore a login (`apps/server/src/auth/session.ts:458-463`, `docs/authentication.md:395-396`). The text, references, focus and thread are what Chat and the comment records already store. So the row holds no usable secret. The table is separate from the sidecar, because a new sidecar key is not readable by the previous release (see [Stage 2](#stage-2-release-safety)).
- **`planner_credentials`.** Columns: `digest` (the SHA-256 of a `chopin_p_` credential, the primary key), machine ID, channel ID and `expires_at`. A row is written when its credential is issued, before the response is sent, so no credential is handed out unless it is durable. `redeem` then looks the digest up in this table instead of the in-memory map (`apps/server/src/harness/remote/machine-planners.ts:95-101`). Rows are deleted when they expire, when their machine ends, and when `withdraw` runs (`apps/server/src/harness/remote/machine-planners.ts:78-84`). No token is stored (see [Security](#security)).

#### Deferred Planner turns

**Scope.** A deferred turn is an acknowledged Planner request whose turn has not started: one queued behind a running turn in normal operation, every one accepted after SIGTERM, and, under `HARNESS=remote`, every one accepted in a hand-over window. The queue limit is unchanged: past 20 waiting items a request is refused before any acknowledgement (`apps/server/src/chat/service.ts:73`, `:1003-1012`, `:1136-1145`, `:1253`; `apps/server/src/comments/service.ts:356-358`), so it creates no row.

Every item that can wait in today's Chat queue (`chat.waiting`) was found from its `push` sites and from the callers of `Chat.instruct`. Five kinds are acknowledged to a person, and each becomes a row:

| Kind             | Enters the queue                                                                                                                                                                                                               | Acknowledged by                                                                                                                            | Today, at a restart                                                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `composer`       | A Chat `@chopin` message (`apps/server/src/chat/service.ts:1013-1025`)                                                                                                                                                         | `chat:send` with `queued: true` (`apps/server/src/chat/service.ts:1025`)                                                                   | Cleared without a notice (`apps/server/src/chat/service.ts:3111`)                                                                                                                 |
| `invoke_planner` | The member message an MCP `invoke_planner` call posts (`apps/server/src/chat/service.ts:819-832`)                                                                                                                              | The call's result, after the message is posted                                                                                             | Dropped; its posted message stays with no answer (`apps/server/src/chat/service.ts:3105`)                                                                                         |
| `invoke_system`  | An `invoke_planner` call with `as: "system"`, through `instruct` (`apps/server/src/chat/service.ts:795-800`, queued at `:1146-1154`)                                                                                           | The call's result, after its notice is posted                                                                                              | Reported `skipped`; its notice stays with no turn (`apps/server/src/chat/service.ts:3105`)                                                                                        |
| `comment`        | A comment note sent to Chopin, in the root (`apps/server/src/comments/service.ts:504-529`) or in a child through the root's Chat (`apps/server/src/chat/root.ts:43-65`), queued at `apps/server/src/chat/service.ts:1146-1154` | `comment:start` or `comment:reply` naming the Planner, after the note is saved (`apps/server/src/comments/service.ts:403-419`, `:449-474`) | Reported `skipped`, so the thread's working mark clears with no reason and nobody is told (`apps/server/src/chat/service.ts:3105`, `apps/server/src/comments/service.ts:546-575`) |
| `draft`          | A task draft from Build (`apps/server/src/chat/service.ts:1253-1264`)                                                                                                                                                          | The `implementation:draft` reply, after the notice of who asked is saved (`apps/server/src/chat/service.ts:1270-1281`)                     | Cleared without a notice; nothing marks the draft ended (`apps/server/src/chat/service.ts:3111`, `:1181-1197`)                                                                    |

The other queue items were acknowledged to nobody, and keep today's handling:

- **Background job turns** (`apps/server/src/chat/job-queue.ts:147-153`). The job is already a durable row. `Chat.close` fails the turn with "The document closed." (`apps/server/src/chat/service.ts:3103`), and the runner may requeue on shutdown without spending failure budget (`docs/background-jobs.md:379-380`).
- **Server-authored turns:** answers to open decisions, decision relinking after a build, and settling a prototyped passage, all through `serverInstruction` (`apps/server/src/main.ts:339-355`, `:357-385`, `:387-400`). They run only under an existing owner and claim none. Decision answers wait in storage and start again after a restart (`apps/server/src/main.ts:388-391`). A relink leaves its cards pending until the next Planner turn (`apps/server/src/main.ts:339-341`).
- **A follow-up on an ended workflow run** (`apps/server/src/chat/service.ts:1739-1750`) and **automatic participation** (`apps/server/src/chat/initiative.ts:99-123`). Neither was asked for by a person, and each is decided again from what the Planner or the conversation reports next.

**Guarantee.** In hosted mode, an acknowledged Planner request of any of the five kinds is never silently dropped, by a deploy or by a crash. Its row is written before the acknowledgement, and it ends as `ended` after its turn ran, or as `interrupted` or `cancelled` with a notice its sender can see. While it waits, it is visible: in the Chat queue, as a thread Chopin is working on, or as a queued task draft. Local mode, which is never handed over, keeps today's in-memory queue (see the last rule below). Each row is in one of five states:

| State         | Entered when                                                                                                                                                                                                                                                                                                                          | What the sender sees                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `waiting`     | Written in the same fenced transaction as the commit that precedes the request's acknowledgement: for a message, before `chat:send` with `queued: true` (`apps/server/src/chat/service.ts:1025`); for the other kinds, see the per-kind rules below                                                                                   | Their request waiting, as behind a running turn today: a message in the Chat queue (`chat:queue`, `apps/server/src/chat/service.ts:584-586`), a thread Chopin is working on, or a queued task draft. If the queue still cannot start because no owner can be resolved `DEFERRED_NOTICE_DELAY_MS` (default 30 s) after route-ready, one Chat notice says what it waits for. The delay is longer than any hand-over's reconnect window, so a deploy whose senders come back in the usual way posts nothing, and strict invisibility holds; a queue that starts before the delay posts no notice at all. The notice says what it waits for: the sender's browser coming back, or any writer's next `@chopin` message. Under `HARNESS=remote` it waits for the attached Planner to reconnect. No new sign-in is needed, because the browser's existing cookie restores the login. Copy follows [`apps/web/DESIGN.md`](../apps/web/DESIGN.md) |
| `started`     | The start rule below holds. The conditional `waiting` to `started` update, under the current lease's fencing, is written in one fenced transaction with the member entry that `pending` adds for a composer message (`apps/server/src/chat/service.ts:2780-2797`), or with the turn's start for the other kinds. So a row starts once | A composer message enters the transcript, and the turn runs as any turn does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `ended`       | The turn ends in the process that started it, with any outcome, including today's failure notice (`apps/server/src/chat/service.ts:2537-2549`)                                                                                                                                                                                        | Whatever the turn showed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `interrupted` | The process aborts the turn at the turn-wait limit, or a later lease holder finds the row still `started` under an older fencing value                                                                                                                                                                                                | A Chat notice says that a restart interrupted the reply, that it was not run again, and that the sender can ask again. It is never replayed, because the turn may already have run tools (`AGENTS.md:246-247`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `cancelled`   | The sender or a Stop cancels it, the channel's agent is reset, the document is archived, the focused child no longer resolves when the row starts, or a comment's thread was resolved                                                                                                                                                 | A notice says that it was cancelled and why: in Chat, and for a comment or a task draft also where it was asked (see the per-kind rules)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

The legal transitions are `waiting` to `started` or `cancelled`, and `started` to `ended` or `interrupted`. `ended`, `interrupted` and `cancelled` are final. Every transition is a conditional update that names the state it expects, so any other transition changes nothing and is logged.

Rules:

- **Persistence before publication.** Every transition is written in one fenced transaction with its Chat notice or member entry, and published only after it commits (`AGENTS.md:214`). The startup reset does not clear rows, because they are not in `agent_state`.
- **Start rule.** A row starts only after route-ready, and only through a check that claims nothing until a login is known to be live. Today `resolveOwner` calls `claimAgentOwner` before it resolves the login (`apps/server/src/chat/service.ts:2299-2311`), and `claimAgentOwner` stores the claimant as owner of any unowned channel (`apps/server/src/storage/postgres/adapter.ts:1276-1290`). Called for an absent claimant, it would pin the document to a login that cannot resolve, and every later writer would get that dead owner back. So the queue first resolves candidate logins without claiming, through `sessions.resolve` (`apps/server/src/auth/session.ts:458-463`), and calls `resolveOwner` only with a claimant whose login just resolved. A failed attempt writes nothing. The row then starts in one of two ways:
  - The document already has an owner whose login resolves. The row runs under that owner, as a queued turn does today, because `claimAgentOwner` claims only an unowned channel and otherwise returns its owner (`apps/server/src/storage/postgres/adapter.ts:1287-1296`).
  - The document has no owner, and the claimant of some row in its queue, not only the oldest, has a live login, which claims it. Under `copilot-sdk` and `atomic`, a login is live again once its browser sends its existing cookie (`apps/server/src/auth/session.ts:380-399`). Any authenticated request does that, including the tab's own reconnect. A paired machine's login is recreated from the machine's grant with no browser (`apps/server/src/auth/machines.ts:55-56`) **(inferred for the owner-binding path)**.
  - The process tries a document's queue at route-ready, whenever a claimant's login is restored, whenever a new Planner request for that document is accepted, and when a remote Planner resumes.
- **Start rule, `HARNESS=remote`.** Only an attachment may claim (`apps/server/src/chat/service.ts:2282-2285`), so rows start once the attached Planner has resumed (`AGENTS.md:139`). Its attach looks the login up in memory (`apps/server/src/harness/remote/attachments.ts:545-551`), so the owner's cookie request must come first.
- **Order and later requests.** A document's rows start in `created_at` order, whatever their kind, as today's queue is one FIFO. A later Planner request joins the queue behind them, is acknowledged as queued, and becomes a row itself. It never waits on an absent claimant. Under `copilot-sdk` and `atomic`, its sender's own live login can claim the document under the start rule. The earlier rows then start first under that sender as owner, and the sender sees them listed ahead of their request, as behind a running turn. Under `HARNESS=remote`, within a hand-over window, a later request is accepted as a row (see [Remote Planner budget](#remote-planner-budget)). Outside one, a later request on a document whose Planner is disconnected is refused before acknowledgement with the existing `planner-not-attached` answer (`apps/server/src/chat/service.ts:998-999`, `apps/server/src/main.ts:946-949`), so it creates no row. Once the Planner resumes, the queue starts in order.
- **Claimant.** A row needs a claimant (its sender, or the document's owner when the row was accepted) only to claim a document that has no owner, and either one coming back is enough. It starts under an existing owner without it. A claimant whose login has ended, by sign-out, expiry, or the startup reset deleting its `web_sessions` row (`apps/server/src/storage/postgres/adapter.ts:677-681`), can no longer claim, and the row waits for an owner like any other.
- **Focus.** A row sent from a child carries the focus accepted with the message. When the row starts, the child is resolved again through storage, as at acceptance (`apps/server/src/chat/service.ts:898-907`). Focus is context, never an authorization grant. The sender's write access was checked when the message was accepted, and a queued message today is not checked again. A row can wait much longer than today's queue, so where the sender's login is live at start, the write check is repeated as for `chat:send`. Where it is not, the row starts on the check made at acceptance. Whether a long wait should require a fresh check is left to the maintainers (open question 15). A child that no longer resolves, because it was deleted or archived, cancels the row with a notice rather than letting it run in the root's context. Otherwise the turn answers in the child's thread, as an undeferred one does.
- **Interrupted rows.** Before starting a document's waiting rows, a lease holder marks every `started` row whose fencing is older than its own as `interrupted`, with its notice. Fencing increases whenever a different owner acquires the lease (`apps/server/src/storage/postgres/adapter.ts:1850-1853`), and each process acquires under a fresh random owner (`apps/server/src/main.ts:2906-2910`). So such a row cannot still be running anywhere: its process no longer holds the lease, and its fenced writes fail `#assertLease`. A turn that ended but whose `ended` write was lost is also reported as interrupted. A wrong notice is better than silence.
- **Comment notes.** A note sent to Chopin is saved with its thread before it is acknowledged (`apps/server/src/comments/service.ts:403-419`, `:449-474`), and its row is written in that same commit as `waiting`. When the Planner is idle, the row moves to `started` at once, in the transaction that posts the instruction's notice. A newer note to the same thread folds into the thread's waiting row, as it folds into the queued turn today (`apps/server/src/chat/service.ts:1127-1134`), so a thread has at most one waiting row. The row stores no text: the prompt is built from the thread when the row starts, as `send` builds it now (`apps/server/src/comments/service.ts:514`), so it reads every note. The claimant is the note author's login session. A thread in a child names that child, which is resolved again through the root when the row starts, as every root call does today (`apps/server/src/chat/service.ts:190-195`). While the row waits, every member sees the thread as being worked on, because a thread's working state is read from the queue (`apps/server/src/comments/service.ts:87-99`), now rebuilt from the rows, also in a new process.
  - A thread resolved before its row starts cancels the row, as `spent` skips it today (`apps/server/src/comments/service.ts:518-519`). The resolution is what members see, so no notice is added.
  - Any other cancellation, and an interruption, clears the working mark with `reason: "failed"`, which reads "Chopin couldn't reply" (`packages/protocol/comment.d.ts:222-232`, `packages/editor/src/comments.tsx:148`). A Chat notice on the comment's card says what happened and that the author can send it to Chopin again. The reason reaches only members connected at the time; the notice is durable.
- **Task drafts.** A draft's row is written in the commit of the notice that says who asked (`apps/server/src/chat/service.ts:1270-1273`), before the `implementation:draft` reply. The row is the document's live draft, so a second press of Build returns it, as it does today (`apps/server/src/chat/service.ts:1250-1251`). It stores the instruction text and `plan_revision`; the instruction reads the latest document when it runs (`apps/server/src/chat/service.ts:1213-1215`). A new process tells members that open the document about a waiting draft row with `implementation:drafting` in state `queued` (`apps/server/src/chat/service.ts:1166-1179`), so Build plan keeps showing it queued. A cancelled or interrupted draft sends `implementation:drafting` with `ended`, and a Chat notice says that the draft did not run and that Build can be pressed again.
- **System `invoke_planner` calls.** The row is written in the commit of the call's notice (`apps/server/src/chat/service.ts:795-800`, `:1072-1077`). It stays out of the visible queue, as a quiet instruction does today (`apps/server/src/chat/service.ts:181-182`). An interruption or cancellation is noted in Chat under that notice.
- **No timer.** A queue with no owner and no live claimant stays `waiting`, with its notice once `DEFERRED_NOTICE_DELAY_MS` has passed, as the remote-owner hold does. The delay only postpones the notice; nothing times out. Any writer's next Planner request, or a claimant's return, starts it. The sender or a Stop can cancel it.
- **Local mode.** Under `AUTH_MODE=local`, deferral is off and the queue stays in memory as today, so the guarantee above does not apply there. `Chat.close` reports or fails queued instructions and job turns (`apps/server/src/chat/service.ts:3102-3106`), and clears queued composer messages and task drafts without a notice (`apps/server/src/chat/service.ts:3111`). Local mode is loopback-only and never handed over.

#### Protocol

- **Browser.**
  - `session:restarting` (`{ kind, ts, reconnectWithinMs }`) is sent before the 1012 close. Older tabs ignore it, because the client ignores unknown kinds (`apps/web/src/wire.ts:305`).
  - `session:hello.build` is optional.
  - The client's `build` query parameter is ignored by older servers.
  - The existing 1012 closes already mean "reconnect", so the meanings agree. `apps/server/src/main.ts:2145` closes with "document state is temporarily unavailable" when the channel lookup fails, and `apps/server/src/main.ts:2156` closes with "document reload required" when a surviving room cannot be planned again.
- **Agent connection.**
  - The `restart-notice` feature is negotiated through `Chopin-Agent-Features` like `resumable-sessions` (`packages/agent-link/src/protocol.ts:23-42`). With it, the server sends `{ type: "restarting", reconnectWithinMs }` before closing with 1012, where `reconnectWithinMs` is the hold's hand-over window. A client that offers the feature reconnects at once, and retries a `resume` refused with `retry` every 250 ms until `reconnectWithinMs` has passed, then returns to its own backoff. Without the feature, the server only closes with 1012.
  - Persisted sessions need no feature, because the `resume` exchange is unchanged.
  - This follows the documented rule: additive features, never a new subprotocol (`docs/agent-connection.md:87-93`).
- **Close codes.** 1012 Service Restart for a deliberate restart. 1001 keeps its link meaning of unresponsive.

#### Compatibility

- **Old tabs** keep running their old JavaScript against the new server. They see today's notice timing, and their chunks are served from the kept assets. Their reconnect needs nothing new, except in two transitional cases that last until each tab reloads.
  - A tab loaded before the Stage 1 client change runs the old `wire.ts`, which treats any 4xx probe answer as a refusal and stops retrying (`apps/web/src/wire.ts:240-246`, `:258-260`). The refusal marker cannot protect it, so a proxy 4xx during the deploy that ships the marker stops those tabs. Mitigation: the proxy and hand-over must not answer 4xx during overlap, and the client change ships before any stage that relies on the proxy gap.
  - After a rollback to a server older than the marker, tabs running the new client would treat that server's genuine 401 and 403 refusals, which carry no marker, as unreachable and retry forever. Chosen design: a probe 401 counts as an authentication refusal with or without the marker, so the sign-in reload still happens. A 403 without the marker stays unreachable, so such a tab keeps retrying with backoff until it reloads. This is accepted for rollback, which already needs a database restore past the newer migrations (see [Stage 2](#stage-2-release-safety)).
- **Older connectors (protocols 2–6)** see a shorter outage, and see 503 instead of a connection error while the new process holds requests. Both already count as `retry` (`apps/connector/src/machine.ts:504`).
- **Agent clients without `restart-notice`** see a 1012 close. The package client treats any close it did not choose as resumable (`packages/agent-link/src/client.ts:577-581`). Such a client resumes on its own backoff. If that is longer than the hand-over window, its document shows the Planner as disconnected when the window ends, as today for a lost connection (open question 3 (h)). Clients that never offered `resumable-sessions` see today's behaviour: their sessions end with the link, and the hold enters its grace period.
- **Rolling back to a release without this stage** leaves the new tables unused. The previous release still refuses the newer migration IDs until [Stage 2](#stage-2-release-safety) relaxes that check.
- **Strict invisibility starts with the first deploy that runs the Stage 1 client.** Tabs opened before it run the old `wire.ts`, which treats any 4xx probe answer as a refusal (see the first bullet above). Their first attempt is also held by the proxy, so a notice appears for such a tab only if that attempt fails.
- **Rollback while deferred turns wait.** The previous release does not read `planner_deferred_turns`, so it would never start or report a row. Before the older release takes over, the newer one therefore resolves every row in its cut: a `waiting` row is cancelled and a `started` row is marked `interrupted`, each with its Chat notice. The rollback tooling asks for this through a drain option, which belongs with [Stage 2](#stage-2-release-safety)'s rollback automation. No row is left to be silently dropped.

#### Proxy guidance

This repository has no proxy configuration, so the proxy is guidance for operators.

- **Readiness.** A proxy that can route on readiness should send new connections only to a ready upstream, and should keep established WebSockets until the server closes them. It must check readiness actively, and the operator sets the server's `HANDOVER_UNREADY_MS` to that check's interval plus a margin. A proxy with only passive health checks learns nothing from the unready window, so it may route to a listener the cut has stopped (see [Hand-over sequence](#hand-over-sequence)).
- **Caddy.** With Caddy, `lb_try_duration` (the docs suggest 5 s to start) lets a request wait for an upstream, and a refused dial is retried for every method. An upstream's answer is passed through as it is: by default, a 502 or 503 from a draining upstream reaches the client. Caddy's current documentation also lets `lb_retry_match` retry on the upstream's status through an `{rp.status_code}` expression, and that worked in Caddy 2.11.7. But retrying a 503 is safe only for a request the upstream did not process, so the design avoids producing one: the old process never refuses a routed request during its cut. Observed with Caddy 2.11.7 against stand-in backends; see [Reference deployment](#reference-deployment).
- **No retry available.** If the proxy cannot hold requests, the server's own standby hold covers only a short gap, and a hand-over becomes visible. The strict decision therefore needs a proxy that holds requests. With stop-then-start, clients rely on their retry loop, and the 4xx fixes above matter most. The [reference deployment](#reference-deployment) sets the Caddy values.

### Stage 2: release safety

The outcome: a bad release is caught before people see it or rolled back automatically, and rolling back is safe because the previous image can run against the new schema and read documents the new image wrote.

#### What changes

- **Readiness from stage 1** becomes the deploy gate.
- **A `container-smoke` CI job** after `container`. CI never starts the image today (`.github/workflows/ci.yml:476-494`). The job:
  - runs the built image against a PostgreSQL service with fake GitHub settings, as the browser suite already does (startup "does not fully validate the GitHub App", `docs/self-hosting.md:674-678`);
  - waits for `/api/health/ready`;
  - fetches `/`, one hashed asset and `/api/session`, and opens a socket upgrade;
  - starts a second container to check the stage 1 hand-over;
  - stops it, asserting exit 0 within the grace and the lease released.
- **Release identity.** Tag server images, for example `server-v*` or an immutable digest per main commit, so "previous release" means something. The registry and tagging used by a hosted deployment live outside this repository.
- **Schema compatibility check.** A `schema-compat` CI job:
  - applies the previous release's migrations, then this release's;
  - boots the **previous** image against the result and runs a smoke subset: create a document through MCP, edit it over the socket, and open a document last written by the **new** image;
  - fails if the previous image refuses.
  - A static check on new migration files flags `DROP`, `RENAME`, type changes and `SET NOT NULL` without a default. A contract step must name, in a header comment, the expand migration it completes and the release since which no code reads the old shape.
- **Relaxing `checked()`.** Today an older binary refuses any unknown applied migration (`apps/server/src/storage/postgres/migrations.ts:135-153`), at startup through `health()` (`apps/server/src/storage/postgres/adapter.ts:788-793`) and in `migrate()` (`apps/server/src/storage/postgres/migrations.ts:155-180`). That makes every rollback a database restore. The proposal:
  - Each migration in `MIGRATIONS` (`apps/server/src/storage/postgres/migrations.ts:16-109`) declares the reader generation it requires.
  - `migrate()` records the highest in a one-row `chopin_schema(min_reader)`.
  - Each binary has a `SCHEMA_READER` constant. A binary accepts unknown migration IDs when `min_reader <= SCHEMA_READER`, still verifies the checksums of the IDs it knows, and refuses otherwise with "this database needs a newer Chopin".
  - **This is the hard point.** A wrong declaration lets old code run against a schema it cannot handle, which is why the CI job must actually boot the previous image. Only releases after this change can be rolled back to without a restore, because the first release with the relaxation cannot help binaries built before it.
- **Sidecar compatibility.** `restoredState` rejects any sidecar with a top-level key it does not know, or `version !== 1` (`apps/server/src/plan/service.ts:544-616`). A release that writes a new sidecar key makes every document it touched unreadable by the previous release. Writing that document back from an older process would also drop the key. The rule:
  - add a sidecar field in two releases. The first reads, preserves and round-trips it without writing it; the second writes it.
  - The compatibility job's "open a document written by the new image" step enforces this.
  - Ignoring unknown keys instead would be the fail-open behaviour `AGENTS.md:430-431` warns against, and would lose data on write-back.
  - The same discipline applies to browser and agent wire messages read by old tabs and clients.
- **Migrations off the critical path.** `migrate()` applies all pending migrations in one transaction (`apps/server/src/storage/postgres/migrations.ts:155-180`), so a data backfill holds its locks for the whole backfill while the old process serves **(inferred)**. Large backfills should run as background jobs after the expand step, as in Stripe's lazy copy. Migrations should set a short `lock_timeout`, so an `ALTER` that waits behind the old process fails and retries rather than queueing every other query behind it. That is general PostgreSQL behaviour, not tested here.
- **Staging.**
  - The image deploys first to a staging deployment with its own database, restored from a recent production backup with credentials scrubbed, so migrations are rehearsed on real data before production. PR previews already exist (`docs/preview-testing.md:3-6`) but use their own small databases.
  - Whether a hosted deployment can afford a scrubbed production copy is an operator question.
- **Automatic rollback** happens in the deploy tooling, outside this repository: watch `/api/health/ready`, the 5xx rate and the client reconnect metrics for a window after the hand-over, and redeploy the previous image tag if they regress, as in the SRE workbook's canary rule. With one writer, the "canary" is the whole deployment for that window. Stage 3 allows a real canary: one new-version process owning a few documents.
- **Feature flags.** Ship risky behaviour behind configuration read at startup, as `BACKGROUND_JOBS` and `CONVERSATION_PLAN` already are (`docs/self-hosting.md:403-407`). Remove a flag one or two releases after it is on everywhere. A flag never gates whether old data can be read.

### Stage 3: several processes

The outcome: N processes share one database. Each root document, together with its children, has exactly one owner process at a time. A deploy starts new processes and moves documents to them one at a time, so each document is unavailable only for its own hand-over.

#### Ownership

- **Unit.** The unit is a **root document**, because a child has no Chat and its Planner turns run on the root's (`AGENTS.md:312-313`, `apps/server/src/main.ts:2521`).
- **Lease.** Each owned root holds a row `document:<rootId>` in the existing generic `storage_leases` table (`apps/server/src/storage/postgres/migrations/001_initial.sql:97-102`). It is acquired on first open, renewed in one batched statement per process every 10 s, and released on hand-over or eviction.
- **Fencing.** `#assertLease` already keys its advisory lock by lease name (`apps/server/src/storage/postgres/adapter.ts:1937`). Passing a document lease to a document's writes therefore gives per-document serialization in place of today's process-wide serialization, which also removes a throughput ceiling **(inferred)**. The writers already receive the lease through closures (`apps/server/src/main.ts:311-314`). Those closures would return the document's lease.
- **Writes that span documents** or are not about a document need an inventory. There are 12 `#assertLease` call sites in `adapter.ts`, plus the experiments, jobs and research stores, and the global job and research advisory lock (`apps/server/src/storage/postgres/adapter.ts:559-565`). Each write becomes fenced by its root document's lease, by a machine lease, or by a small coordinator lease. Child creation stays inside the root's lease.
- **Processes.** `chopin_processes` has one row per process: `id` (the process lease owner), internal address, build, `ready`, `draining`, `expires_at`. This is how a process finds an owner to forward to, and how a draining process is excluded from new acquisitions.
- **The old writer lease** becomes a **coordinator lease** for process-wide singletons only: session cleanup, experiment sweeps, research recovery, and startup work that today runs once per start. Migrations keep their own advisory lock (`apps/server/src/storage/postgres/migrations.ts:115`).

#### Routing

Every process accepts every request, finds the owner, and serves the request itself or forwards it. Forwarding goes over an authenticated internal hop that is never public, keeping one public origin and port as `docs/self-hosting.md:12-16` requires. Proxy hashing on `channel` is an optional optimization measured later, not a correctness mechanism.

- **Browser `/ws?channel=`** (`apps/web/src/wire.ts:73-74`): resolve the root, then serve locally or relay frames to the owner. The owner authenticates the original cookie itself.
- **`/ws/sidebar`:** served by any process. Document owners publish key-only change notices (under 8000 bytes, per the PostgreSQL `NOTIFY` limit) and each process re-reads. A reconnecting sidebar reconciles from tables, because `NOTIFY` is not redelivered.
- **Document HTTP routes:** reads that do not need room state are served from the database anywhere. Mutations are forwarded. Each route needs classifying.
- **`/mcp`:** the receiving process parses the tool call and forwards document mutations to the owner. MCP sessions are in the database (stage 1). `invoke_planner` runs on the owner, which keeps the per-document hourly limit (`apps/server/src/mcp/invoke.ts:36-44`) correct.
- **Agent connection `/api/v1/agent`:** accepted anywhere and relayed to the owner after `attach` names the document. An optional `Chopin-Agent-Document` request header, added as a new feature, lets a newer client be routed before the upgrade.
- **Connector `/api/connector/*` and `/connector/mcp`:** these are per machine, not per document.
  - A machine's long poll is held by the process that owns a `machine:<id>` lease.
  - Document owners queue work offers in a table and notify.
  - Build heartbeats name their document (protocol 6) and go to its owner.
  - Pairing keys (`apps/server/src/experiments/pairing-keys.ts:45-49`) and run-token maps (`apps/server/src/experiments/connections.ts:136-138`) move to the database, or to verification by derived key where that already exists.

#### Deploy by moving documents

1. New-version processes start, register, become ready and acquire nothing yet.
2. The old process D marks itself `draining`, so it acquires no new documents and readiness goes off for new routing.
3. D moves its documents one at a time, idle ones first and ones with a running turn last. For each document it:
   - defers new turns for that document;
   - waits up to the turn limit;
   - runs `Service.drain`;
   - persists Planner holds;
   - releases that document's lease;
   - sends that document's sockets `session:restarting` and closes them with 1012.

   Clients reconnect with jitter to any process, and the next open acquires the lease on a non-draining process. D paces releases, for example 5–10 documents a second, to avoid a reconnect and checkpoint surge, as Figma defers its checkpoints.
4. D releases the coordinator lease if it holds it, then exits.

Waiting for one document's turn no longer blocks any other document, which resolves stage 1's main tension. Several versions run at once for minutes in every deploy, so stage 2's compatibility rules become mandatory, and the internal forwarding protocol needs its own version.

The stage 1 budget applies to each document's move as well. A document's new owner is already warm, so the move is budgeted like a single-process hand-over, and the two-process test measures it per document. This revision does not re-estimate stage 3.

#### Split brain and fencing

Suppose a paused process (a long garbage-collection pause or a VM freeze) outlives its document lease while another acquires it with `fencing + 1`. The stale process's next write fails `#assertLease`. It must then close **that room only**, and tell its sockets to reconnect. Today a persistence failure drains the whole process (`apps/server/src/main.ts:315-318`), which must change. Clients replay unacknowledged updates to the new owner. A Planner turn on the stale owner fails and is not replayed. Broadcasts the stale owner sent before noticing were all of committed data, because commit precedes acknowledgement and relay (`apps/server/src/plan/service.ts:1846-1881`).

#### Data model, protocol and compatibility

- **Data model.** These are all expand migrations.
  - Document leases are rows in the existing `storage_leases` table, so they need no schema change.
  - A new `chopin_processes` table, described above.
  - A machine work queue, and a pairing-key table, replacing the in-memory maps.
  - An `owner_fencing` column on `agent_state`, so an owner binding records the document lease it was made under.
  - Stage 1's `planner_link_holds` and `mcp_sessions` are reused as they are.
- **Protocol.**
  - The internal forwarding protocol is new, private and versioned, so a forwarding process and an owner of different builds can refuse each other clearly instead of misreading frames.
  - On the public side, the only new element is the optional `Chopin-Agent-Document` header, offered as an agent-connection feature. `session:restarting` and 1012 from stage 1 are reused when a document moves.
- **Compatibility.**
  - Browsers, connectors and agent clients of any supported version need no change, because forwarding is invisible to them. They still reach one origin, and a document move that stays inside stage 1's 1.5 s budget shows them no notice.
  - Several server versions run at once during every deploy, so the stage 2 rules (expand-only schema, two-release sidecar fields, the browser and agent support windows) are required, not optional, from this stage on.

#### Hard and unknown

- **Forwarding WebSocket frames** adds a hop, a failure point and head-of-line delay. Its cost in Bun is unmeasured.
- **Mutating HTTP and MCP calls caught by a hand-over** need idempotency. Some document operations have operation IDs (`docs/architecture.md:494-495`), but not every route does.
- **Database connections.** Each process uses a pool of up to 10 connections plus one lease connection (`apps/server/src/storage/postgres/adapter.ts:504`, `:525`), so N processes need N×11 plus migrations and `LISTEN`. Whether a pooler sits in front, and in which mode, is unknown.
- **The inventory of process-local singletons** is long: timers, recovery loops, caches and announcement queues across `main.ts`. Each needs an owner.
- **Atomic's local state**, described in the table above.
- **Load balancing** of documents across processes. Hot documents are not addressed by this design.

#### Tests, rollout and size

- **Tests:**
  - storage contract tests for document leases: takeover, fencing, a stale write refused, batched renewal;
  - a two-process lifecycle test in which a document moves while a tab edits it and a Planner holds a question;
  - forwarding unit tests;
  - the deploy-under-load test from stage 1 with two to three processes and continuous moves;
  - a chaos variant that kills a process (SIGKILL) and pauses one (SIGSTOP) past its lease.
- **Rollout:** behind `PROCESSES=multi`. Start with two processes where one owns everything, to prove forwarding, then spread ownership.
- **Size: XL, about 16–26 engineer-weeks (4–6 months).** This is the least certain estimate in this document, and should be re-estimated after the singleton inventory and a forwarding prototype.

### Stage 4: connected machines

The outcome: updating the connector or a Planner backend never stops running work, and a stated window keeps older connectors and agent clients working.

#### Update only when idle

- `chopin update` installs the new binary and, for a running service, sets the existing `restart-pending` state (`apps/connector/src/service.ts:1048`, `:1099`, `:1188`) instead of restarting at once (`apps/connector/src/service.ts:1435-1464`). The running connector notices, for example through the stop-request file it already watches on Windows (`apps/connector/src/service.ts:1466-1481`) or by comparing its executable. It restarts itself only when **idle**: no build or investigation running, and no Planner backend holding a live run or an open question.
- `chopin update --now` keeps today's behaviour.
- The terminal and `chopin status` say "update ready, waiting for the current build to finish".
- **Optional automatic update.** A service can install the server-recommended release (`GET /api/connector/version`, `apps/server/src/experiments/routes.ts:1252-1253`) when idle. This is a product and supply-chain decision; see [Open questions](#open-questions). Downloads are already verified like the installer's (`docs/chopin-cli.md:683-684`).

#### Resume paused runs afterwards

- **Builds** need nothing more, because idle means none is running.
- **Planner backends** are external commands the connector starts per document (`apps/connector/src/connection.ts:304`; `apps/connector/src/config.ts:29-31`). They attach over the agent connection. Atomic workflow runs can be paused and later resumed from their journal (`docs/hosted-agent.md:852`, `:868-870`).
- With stage 1's persisted holds, a backend can survive its own restart, provided it:
  - stops without `detach`, which would end its sessions for good;
  - saves the session IDs and waited-on request IDs from the `resumption` that the package client produces (`packages/agent-link/src/client.ts:543`, `:577-581`) to its state directory. Only those IDs can be saved. A pending ask also holds `settle` and `route` functions (`packages/agent-link/src/client.ts:98-118`), which no file can hold;
  - on restart, rebuilds a resumption from those IDs and passes it to the next `connectAgent` as `resume`, then waits again for each saved request ID.
- `packages/agent-link` gains a serializable descriptor of a resumption, holding its session IDs and waited-on request IDs, and a function that rebuilds a `Resumption` from one. The backend supplies the callbacks for each rebuilt ask, because the closures cannot be saved. The descriptor is a client-side type, so this needs no wire change.
- Whether a given backend can reload its Atomic sessions is backend-specific. That code is outside this repository.

#### What cannot be done to a running agent

The connector owns its coding agent's standard input and output over ACP (`apps/connector/src/acp.ts:63`, `:94-95`), so replacing the connector process ends that agent's conversation. Chopin should not try to hand a live ACP session to a new connector. The timers that bound an absence remain:

- the connector keeps an agent running for 10 minutes without reaching Chopin (`apps/connector/src/reconnect.ts:62`);
- the connector resets its ladder after a connection has been healthy for 60 s (`apps/connector/src/reconnect.ts:45`);
- the server waits `CHOPIN_BUILD_RESUME_MS` (10 minutes by default, `apps/server/src/config.ts:314`) for a machine after its own restart;
- the server then allows 60 s once the machine is back (`apps/server/src/tasks/connector.ts:48`).

A connector update during a build would exceed none of these if the build itself survived, but it does not survive. Hence idle-only.

#### Support window

- **Connector protocol.**
  - Keep `max - min >= 2`, so the current protocol and the two before it are accepted. Today the range is [2, 6] (`apps/server/src/experiments/routes.ts:232`).
  - Raise `min` only after server logs, which already receive version and protocol headers on every request (`packages/protocol/connector.ts:5-6`), show no machine below it for 30 days.
  - Raise it only after one release advertised it: `GET /api/connector/version` gains `deprecatedBelow` and a date. The connector reads only `version` today (`apps/connector/src/update.ts:175-177`), so an extra field is safe.
  - Never refuse calls belonging to a build already running. Refuse new work and pairings with today's 409 (`apps/server/src/experiments/routes.ts:1246`).
- **Agent connection.**
  - Keep `chopin.agent.v1` while any client in the logs still offers only it, and add features additively (`docs/agent-connection.md:87-93`).
  - A future `v2` is served beside `v1` for at least two server releases.
  - `refused` with `unsupported-version` and 4426 (`packages/agent-link/src/protocol.ts:59`) remains the last resort.
- **Browser.** Support the previous browser protocol for at least one release, because tabs stay open for days. The `build` parameter from stage 1 shows how many old tabs remain.

#### Failure modes, tests, rollout and size

| Failure                                       | Handling                                                                        |
| --------------------------------------------- | ------------------------------------------------------------------------------- |
| A machine is never idle                       | The update waits, and `chopin status` says so. `--now` is available             |
| A backend restarts without a saved resumption | Today's behaviour: its sessions end and its questions are cancelled client-side |

- **Tests:** connector unit tests for the idle gate and restart-pending, and a round trip of the resumption descriptor that rebuilds the waiters from it. An end-to-end test with the fake connector updating mid-build should show the build finishing first, and a backend resuming an open question across its own restart.

## Reference deployment

This section shows one shape that gives the overlap stage 1 needs. It is an example for operators, not configuration that this repository ships. The known hosted deployment runs Docker Compose with Caddy 2 on one VM, deployed by a script that runs `docker compose pull` and then `up --detach`. Its operators control the proxy and can start a second container before stopping the first. Its own values are not reproduced here.

**That deploy script must change.** After an image change, a plain `docker compose up --detach` recreates every service whose image or configuration changed. In the two-slot project below, both slots use the same image, so it recreates `chopin-a` and `chopin-b` at once and stops the serving slot together with the idle one: a stop-then-start deploy with no overlap. It would also recreate the database or the proxy if their images had been pulled. The per-slot sequence at the end of this section replaces both commands. Observed with Docker Compose 5.5.1 on a throwaway two-slot project of `sleep` containers sharing one image tag: after the tag moved to another image, plain `up --detach` recreated both slots, while `up --detach --no-deps chopin-b` recreated only `chopin-b` and left the other slot's container running.

Two named service slots, `chopin-a` and `chopin-b`, share one image, one environment file and one database. Both set `HANDOVER=wait`, so the idle slot waits in standby on the held lease instead of exiting 1 (`apps/server/src/main.ts:2911`, `:2934-2940`). Both also set `HANDOVER_UNREADY_MS` to Caddy's health interval plus 50 ms. A deploy starts the idle slot, waits until it reports warm, and then stops the old slot. Only the lease holder is routed to.

```yaml
x-chopin: &chopin
  image: ${CHOPIN_IMAGE}
  env_file: .env
  environment:
    HANDOVER: wait
    HANDOVER_UNREADY_MS: "300" # Caddy's health_interval plus 50 ms
  depends_on:
    db:
      condition: service_healthy
  expose:
    - "8787"
  restart: unless-stopped
  stop_grace_period: 30s
  healthcheck:
    test: ["CMD", "bun", "-e", "let r=await fetch('http://127.0.0.1:8787/api/health/live');process.exit(r.ok?0:1)"]
    interval: 10s
    timeout: 3s
    start_period: 10s
    retries: 3

services:
  db:
    # as in compose.yaml
  chopin-a:
    <<: *chopin
  chopin-b:
    <<: *chopin
  caddy:
    image: caddy:2
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
    depends_on:
      - chopin-a
      - chopin-b

volumes:
  caddy-data:
```

The Caddy site block is the operator's. Its upstream block is:

```caddyfile
reverse_proxy chopin-a:8787 chopin-b:8787 {
	lb_policy first
	lb_try_duration 5s
	lb_try_interval 100ms
	health_uri /api/health/ready
	health_interval 250ms
	health_timeout 1s
	health_status 200
}
```

The deploy script, which lives outside this repository, does the following:

1. `docker compose pull chopin-a chopin-b`, so a newer database or proxy image is not pulled as a side effect. This replaces the plain `docker compose pull`.
2. `docker compose up --detach --no-deps` for the idle slot only, for example `docker compose up --detach --no-deps chopin-b` while `chopin-a` serves. This replaces the plain `up --detach`. Naming one service limits the recreation to it, and `--no-deps` keeps Compose from recreating the database. Compose recreates a single service's container by stopping the old one first **(inferred)**, so the separate slot name is what makes overlap possible.
3. It waits until the new slot's `GET /api/health/live` returns 200 with the status word `standby`, or `ready` when the serving slot had already died or its lease had expired, so the new slot took over at once. Without `HANDOVER=wait` the slot exits instead, and this step never succeeds.
4. `docker compose stop chopin-a`. This sends SIGTERM and waits up to 30 s. The old slot keeps serving through its turn wait, runs its cut, and releases the lease. The new slot becomes route-ready within the budget.
5. The next deploy uses the other slot.

Points to note:

- **Liveness and readiness.** `live` answers while the process runs, and Docker's `HEALTHCHECK` uses it. `ready` answers 200 only for the lease holder, after its lease-bound startup, and Caddy's active check uses it. The holder turns `ready` off at the start of its cut, and keeps serving through its 300 ms unready window, which covers Caddy's next check. A standby is live but not ready, so Caddy never routes to two writers.
- **Hold.** `lb_try_duration` must cover the cut's first steps plus the budget: the 300 ms unready window, up to the 1 s in-flight bound, and about 750 ms from the release to adoption. 5 s, the docs' suggested start, leaves room. A request still unrouted after it gets an error from Caddy, and the status it gets is open question 1.
- **Health and retry intervals.** Together they are the largest terms in the budget. With 500 ms and Caddy's default 250 ms, adoption could take about 1.15 s, against the browser's 1.2 s limit. The values 250 ms and 100 ms are proposals that the restart test must measure. Each check is one small request per slot every 250 ms.
- **Health check timeout and failures.** Caddy marks an upstream down after `health_fails` failed checks in a row, 1 by default, and a check that takes longer than `health_timeout` fails ([Caddy's `reverse_proxy` documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)). With one failure enough, a slow answer from the only ready slot would mark it down for a health interval, and Caddy would hold every new request meanwhile. During the reconnect burst at 1.2 s that hold would use up the upgrade's 300 ms margin. `ready` should answer from state the process already holds, checked when it became route-ready, rather than run a query on every check, so a slow answer means the process stalled. The reference therefore sets `health_timeout 1s`, so that only a stall longer than a second marks the slot down. It keeps `health_fails` at 1, because the cut's 503 is answered at once and must take effect after one check. `health_fails 2` is the alternative: it tolerates one failed check of any kind, but needs two 503 answers at the cut, so `HANDOVER_UNREADY_MS` would grow to two intervals plus the margin (550 ms). Both values are proposals for the load test to measure.
- **Retries.** The old slot never refuses a routed request during its cut, and it answers nothing after it releases the lease. A dial to a stopped slot is refused, and Caddy retries a refused dial for every method (see [Reference review](#reference-review)). So the reference needs no `lb_retry_match`. A 503 from an upstream would reach the client unless `lb_retry_match` retried it on its status, which is safe only for a request the upstream did not process.
- **Observed with stand-ins.** A script outside the repository ran `caddy:2` (Caddy 2.11.7) with this upstream block in front of two small Python HTTP servers standing in for the slots, while six clients sent alternating GET and POST requests through it. Every count below is from retained logs of these runs:
  - With the cut in this design's order (readiness off for a fixed 300 ms window, then the listener stopped, in-flight requests finished, and the release), 30 runs gave no error in 12,702 requests. Each window answered exactly one readiness check with 503, and the new slot served held requests 105 to 161 ms after it turned ready. These runs used `health_timeout 1s`.
  - With the listener stopped while Caddy still counted the slot ready, 9 of 30 runs each had one failed request, 9 in 12,953 requests. All 9 were POSTs answered 502 by Caddy. The likely cause is a connection the kernel had accepted but the process had not, reset when the listener closed **(inferred)**. That is why the unready window comes first.
  - With the old slot answering 503 after readiness turned off, the 503 reached the client. With `lb_retry_match` set to retry on that status, it was retried. Each was one run.
  - With a 500 ms health interval and a 250 ms `lb_try_interval`, held requests reached the new slot 321 to 358 ms after it turned ready, in 3 runs, against 105 to 161 ms with the reference values.
  - These runs used stand-ins, not Chopin. They show how Caddy behaves, not how fast Chopin hands over.
- **Grace.** `stop_grace_period: 30s` caps the drain. The turn wait plus the cut must finish well inside it. The turn-wait value is open question 5.
- **Shared settings.** Both slots share `SESSION_ENCRYPTION_KEY`, `APP_ORIGIN`, `PREVIOUS_ORIGINS` and the App client ID. A deploy must never change them together with a version (see [Security](#security)).
- **Not run.** Chopin was not run in this shape. `caddy validate` accepted the upstream block above inside a minimal site block (Caddy 2.11.7, "Valid configuration"). `caddy validate` on the operator's own site block and a two-slot restart on a staging copy are required before rollout.

## Cross-cutting concerns

### Order and dependencies

- Stage 1's client fixes (refusal marker, 1012, asset 404, kept assets) and readiness endpoints help even with today's stop-then-start, so they come first.
- Stage 1's overlap mode needs expand-only migrations. Until stage 2's check exists, a release with a contract step uses stop-then-start.
- Stage 2 is required before stage 3, because stage 3 runs mixed versions in every deploy.
- Stage 4 depends on stage 1's persisted holds only for backend resumption. Its idle gate can ship any time.

### Observability

Chopin has no metrics endpoint today. These are proposed as structured log lines first.

- **Per hand-over:** SIGTERM to the cut, the cut's phases (the unready window with its count of 503 readiness answers, listener stopped, in-flight requests finished, lease released), release to lease acquired, route-ready, adoption by the proxy, and the gap each client saw. Also the number of requests held in standby, each request still running at the in-flight bound, each hand-over past 1.5 s, and each remote Planner's hand-over window: resumed within it, with the time, or missed, with the cause.
- **Per client:** reconnect latency, reported by the client on its next `plan:open` or socket URL; how often a notice was shown; outbox replays; `replaced` resets, which must be zero in a deploy; build IDs of connected tabs; and 404s on `/assets`.
- **Planner:** deferred-turn rows by kind and outcome (`ended`, `interrupted`, `cancelled`) and the age of the oldest `waiting` row per document; turns finished and interrupted by a deploy; remote `resume` outcomes (resumed, retry, nothing); requests accepted in a hand-over window; and `owner-unavailable` job pauses.
- **MCP and connectors:** `session-required` answers, connector refusals by protocol, builds resumed and ended after a restart.
- **Stage 3:** document hand-over time, forwarded connections and their latency, lease renew failures, fencing conflicts, and database connections in use.

### Security

- **Admission is not authorization** (`AGENTS.md:129-133`). Forwarding must never let the receiving process's checks stand in for the owner's. The owner re-runs admission and repository role on the original credential.
- **The internal forwarding hop carries plaintext credentials**, so it must be protected to match. Forwarding passes on what the caller sent: a browser session cookie, a machine or Planner credential, or a GitHub bearer on `/mcp` and on the agent connection (`apps/server/src/harness/remote/endpoint.ts:157-178`, `docs/agent-connection.md:33`). The hop must be:
  - **encrypted** with TLS. A private network isolates the hop but does not encrypt it;
  - **mutually authenticated**, with a per-process certificate or key that each process pins for its peers, so only processes of this deployment can send or read forwarded requests. This key is separate from `SESSION_ENCRYPTION_KEY`. A key derived from it under a new HKDF context, as `apps/server/src/auth/session.ts:255-259` does for sessions, can authenticate messages but cannot protect a bearer already sent in the clear;
  - **unlogged**: request logs, error reports and diagnostics omit the `Authorization` and `Cookie` headers and any forwarded field that carries a credential.
  - The alternative is to authenticate the caller once at the receiving process and forward only a short-lived signed identity, with no bearer on the hop. That removes plaintext credentials from the hop, but it lets the receiving process's verification stand in for the owner's, which the rule above forbids. It is open question 14.
- **Every process must share** `SESSION_ENCRYPTION_KEY`, `APP_ORIGIN`, `PREVIOUS_ORIGINS` and the App client ID. Changing the key invalidates hosted logins (`docs/self-hosting.md:387`), and changing the origin signs everyone out (`docs/self-hosting.md:731-733`). A deploy must never change them together with a version.
- **Persisted Planner holds, deferred turns, MCP sessions and credential digests hold no usable secret.** Holds and MCP sessions are identifiers bound to a user and a document. A deferred-turn row holds a login session ID, which cannot restore a login, and the request's text, references, focus, thread or plan revision, which Chat and the comment records already store. A persisted Planner credential is stored only as its SHA-256 digest, as machine bearer tokens already are (`apps/server/src/auth/machines.ts:59-60`, `:102`). The credential carries 256 random bits, so a dump of digests cannot be replayed. Each row expires with its credential, and is deleted when its machine ends or the backend is withdrawn.
- **Restoring a login from the database without its cookie,** for a remote Planner's resume, would change a documented security property (`docs/authentication.md:395-396`). This design does not do it, and open question 4 records that decision.
- **Health endpoints** are unauthenticated and reveal only a status word.

### Out of scope

- Multi-region deployment, database high availability and failover, and PostgreSQL major-version upgrades.
- Zero downtime for local mode or source deployments run by hand.
- Resuming an in-process harness turn, or an ACP agent session across a connector restart.
- Load-based rebalancing of documents, and very large single documents.
- The deployment platform's own configuration (proxy, registry, Coolify). The known hosted deployment's configuration lives outside this repository. The [reference deployment](#reference-deployment) shows the shape the design needs.

## Open questions

1. **Proxy and platform.** Partly decided. The known hosted deployment runs Docker Compose with Caddy 2 on one VM, deployed by a script that runs `docker compose pull` and then `up --detach`, with `stop_grace_period: 30s` and a container health check. Its operators control the proxy configuration and can start a second container before stopping the first, so overlap is possible. The [reference deployment](#reference-deployment) shows the shape. Caddy's hold, active health checks and retry of refused dials were observed with Caddy 2.11.7 in front of stand-in backends, not in front of Chopin. Still open: what the proxy answers, and with what status, after its hold expires while no upstream is ready. The design needs a 5xx there and never a 4xx (see [Compatibility](#compatibility)). This must be checked on the deployment before stage 1 ships.
2. **Coolify.** Not applicable to the known hosted deployment, which does not use Coolify. The design is platform-neutral and does not depend on the answers. The questions remain for any other deployment that uses Coolify: does a redeploy stop then start or overlap, does it honour `stop_grace_period`, and which health check does it route on?
3. **"Invisible." Decided: strictly invisible.** No notice may show within the 1.5 s reconnect grace, so a deploy needs process overlap: the new process starts, warms and waits on the lease beside the old one. The forced consequences, applied in [Hand-over sequence](#hand-over-sequence), are:
   - (a) The proxy holds or retries requests while no upstream is ready, for `lb_try_duration`. The server holds requests only as a fallback.
   - (b) A warm standby waits on the writer lease without serving, and becomes route-ready only after it acquires the lease.
   - (c) Checkpoints and commits run while the old process keeps serving, before the cut.
   - (d) Running turns finish while the old process keeps serving, bounded by the stop grace. The bound is left to open question 5.
   - (e) The cut is ordered so the old process never refuses a routed request and answers nothing after the release. Readiness turns off for a fixed unready window that covers the proxy's next check, then the listener stops, then in-flight requests finish, then the lease is released and sockets close. The window is fixed because a process cannot count the proxies that check it; a window with no check is logged, never waited out. The browser's probe and its 1.2 s rescue point make adoption within about 1.2 s of the loss the real target, so the reference uses a 250 ms health interval and a 100 ms retry interval.
   - (f) When the budget is exceeded, the fallback is today's "Reconnecting…" notice after 1.5 s, logged per hand-over. The design allows no planned miss, so the release test counts zero notices, and a production miss is a defect to investigate. The thin margin is the upgrade burst at 1.2 s, which the load test must cover.
   - (g) The first deploy that runs the Stage 1 client cannot be fully invisible to tabs already open (see [Compatibility](#compatibility)).
   - (h) Remote Planners have bounded exceptions. A deploy closes every remote Planner's link, and the browser shows every Planner state except `attached` as an offline Planner. The [hand-over window](#remote-planner-budget) keeps a hold whose link the cut closed shown as attached, and accepts requests for it as rows, for `HANDOVER_PLANNER_WINDOW_MS` (proposed: 10 s). Members see a change only when the window ends without a resume, and only these cases cause that:
     1. The owner's login cannot come back within the window. Open question 4 keeps restoring a login from its browser cookie only, so a person who runs the Planner from a command line, with no Chopin tab open in the browser that holds the owner login, cannot be restored by the deploy. A hidden tab whose timers the browser throttles may also come back late **(inferred)**.
     2. The agent client does not resume within the window: one that does not offer `restart-notice` and backs off for longer, or one that offers it and is still slower.
     3. A client that never offered `resumable-sessions` loses its sessions at every restart, as today, and its hold enters the grace period, which members also see as an offline Planner.

     Each case happens at most once per deploy for each document whose remote Planner is in it, and never for a paired machine's Planner in hosted mode, whose login needs no browser. Each is logged per hand-over as a remote-Planner miss with its cause. Members then see what a lost connection shows today, and nothing they sent in the window is lost. These cases are exceptions to the zero-notice release gate, which is measured with a client that follows the `restart-notice` rule and an owner tab open.
4. **Remote Planner restart. Decided: persist, and restore logins from the browser cookie only.** Remote Planner sessions are persisted in stage 1. A login is restored only from its browser cookie, so `docs/authentication.md:395-396` is unchanged. A paired machine's Planner needs no browser: its login is recreated from the machine's own grant (`apps/server/src/auth/machines.ts:55-56`, `:190-200`). Under `AUTH_MODE=local`, machines hold no grant and must borrow a browser sign-in, so that case keeps today's behaviour (`apps/server/src/harness/remote/machine-planners.ts:124-127`). A person who attached from a command line while a browser login of theirs existed, and has no Chopin tab open in that browser during the deploy, has no cookie in the restarted process. For them, exactly this happens:
   - Their hold is rebuilt and shown attached through the hand-over window. Requests members send in it are acknowledged and recorded as `waiting` rows.
   - Their client's `resume` is refused with `unavailable` and `retry: true`, which the client retries (`docs/agent-connection.md:1010-1011`).
   - When the window ends, the document shows its Planner as disconnected, and new Planner requests are refused with `planner-not-attached`, as for any lost connection. The hold, with its open questions and held stops, and the rows accepted in the window wait with no timer. This is open question 3 (h), case 1.
   - When that person opens Chopin in the browser that holds the owner login, its first authenticated request restores the login (`apps/server/src/auth/session.ts:380-399`). The client's next retry resumes, and the waiting rows start in order.
   - Signing in again in another browser creates a different login, which the hold does not accept, because a hold names its owner's login session (`apps/server/src/harness/remote/attachments.ts:524-526`) **(inferred for a rebuilt hold)**. The client can then attach afresh, which ends the kept sessions as attaching without `resume` does today.
   - If the owner login ends instead, by sign-out or expiry, the hold ends as a sign-out ends it today (`docs/agent-connection.md:1012-1021`), and the rows wait for the document's next attached Planner.
5. **Turn limit.** What limit on finishing a running Planner turn before a deploy proceeds is acceptable, given the platform's stop grace?
6. **Close code under load.** Bun 1.4.4 sends 1001 on `server.stop(true)`; that was observed for this document. Does any Bun or proxy behaviour change the code a client sees under load? Should Chopin close each socket itself with 1012 before stopping, as proposed?
7. **Unknown MCP sessions.** Should an unknown MCP session ID get the specification's 404, so conforming clients re-initialize, or keep today's per-tool `session-required`?
8. **PostgreSQL connections.** Is PgBouncer, or another pooler, in front of the hosted database, and in which mode? That decides whether `LISTEN`/`NOTIFY` and session-level advisory locks are usable. What `max_connections` can the database give N processes at 11 connections each?
9. **Stage 3 routing.** Is in-application forwarding acceptable, or would maintainers rather route at the proxy, accepting its limits for agent and MCP traffic?
10. **Atomic state.** For `HARNESS=atomic`, will a hosted deployment mount `/var/lib/chopin` as a volume, and later share it between hosts, or should Atomic documents stay on one host?
11. **Connector support.** How long should old connectors be supported: protocols, months, or both? Should services update automatically when idle?
12. **Server releases.** Are there, or will there be, tagged server releases and an image registry that CI can address as "the previous release"?
13. **Internal forwarding keys.** Are per-process certificates or keys preferred over one shared internal secret, and how are they rotated? Deriving a key from `SESSION_ENCRYPTION_KEY` cannot encrypt the hop (see [Security](#security)).
14. **Forwarding transport.** Should forwarding keep the caller's credentials on an encrypted, mutually authenticated hop, as this design does, or should the receiving process verify the caller once and forward only a short-lived signed identity? The second keeps bearers off the hop, but the owner would then run admission and repository role with its own credentials, which may not give the same answer as the caller's token.
15. **Stale deferred turns.** A deferred row has no timer, so it can start long after its sender's write access was checked. Should a row whose sender's login is not live at start run on the check made at acceptance, as this design proposes, or wait until that login returns, or be cancelled with a notice after a stated age?
16. **Rows for every Planner request.** Rows are written only for requests that could not start at once, so a turn that started immediately and was running when a process was killed past its stop grace, or crashed, ends with no report. Should every accepted Planner request get a row, so a kill or crash reports every running turn as interrupted, at the cost of a write on every request?

### What changed in this revision

- **Stage 1 grows from 8–11 to 14–17.5 engineer-weeks** (11.5–14 without persisted holds, from 5–7). An earlier draft of this revision said 12–15; covering every acknowledged kind of Planner request and the remote-Planner hand-over window added 2–2.5 weeks to it.
  - Strict invisibility needs a warm standby, two readiness states and an ordered cut. The cut turns readiness off for a fixed unready window, then stops the listener, finishes in-flight requests, and only then releases the lease. So the hand-over item grows from 2 to 3–3.5 weeks.
  - Deferred turns become a durable Planner queue in normal operation, not only during a drain. A request queued before SIGTERM was acknowledged from memory, so only a write at acknowledgement covers it. The queue covers five kinds of acknowledged request, not only Chat messages: comment notes sent to Chopin, task drafts and system `invoke_planner` calls were dropped silently too. It also needs five states with fencing-based recovery of interrupted turns, a claim by any queued claimant so a later request never waits on an absent one, the child focus revalidated at start, comment folding and working state read from the rows, retried sends and rollback resolution. That item grows from about 1 to 3.5–4.5 weeks.
  - Persisted holds gain the hand-over window, so that a deploy does not show remote Planners as disconnected. That item grows from 2–3 to 2.5–3.5 weeks.
  - The restart tests grow from 1.5–2 to 3–3.5 weeks, for zero-notice assertions under overlap, a proxy in the loop, crash-window, child-focus and comment-note cases, and a remote Planner resuming within its window.
  - The parts add to 14–17.5.
- **Stage 2 grows from 4–6 to 4.5–5.5 engineer-weeks.** `container-smoke` now checks a two-slot hand-over with the warm-standby state, so smoke grows from about 1 to 1.5 weeks. The parts (1.5, 2–3 and 1) add to 4.5–5.5. The earlier upper bound of 6 did not match its own parts.

- **Corrections made while revising.**
  - The owner-missing `resume` case must answer `unavailable` with `retry: true`, because `sign-in-required` ends the link (`apps/server/src/harness/remote/link.ts:95`, `:1261`).
